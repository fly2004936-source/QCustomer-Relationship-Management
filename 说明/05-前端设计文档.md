## 二、外壳：`App.vue`

### 2.1 视图切换不用路由

```js
const view = ref('workbench')   // workbench | graph | analytics | crud | gallery | demo
```

模板里就是 `v-if` / `v-else-if` 分支：

| `view` | 组件 | 说明 |
| --- | --- | --- |
| `workbench` | `WorkbenchView` | 数字桌面（默认） |
| `graph` | `GraphView` | 客户人员组织架构 + 项目作战视图 |
| `analytics` | `AnalyticsView` | 数据分析与可视化驾驶舱（KPI 带 + 12 面板） |
| `crud` | `CrudView` | 通用数据管理（62 张表） |
| `gallery` | 内联模板 + `MiniPreview` | 11 套风格画廊 |
| `demo` | `DemoPage` | 单风格示例页 |

**为什么不用 Vue Router**：桌面程序没有 URL 语义需求，只有 6 个视图，且切换时要保留上一个视图以便返回（`prevView`）。一个 `ref` + `v-if` 比引入路由省一层心智负担。

细节：切到 `crud` 时会用一个 `key` 让 `CrudView` **重新挂载**，保证「同一张表、不同入口进入」都能拿到干净状态。

| 02 | `linear` | Linear 极简 | dark | 近黑、靛紫渐变 CTA、无阴影 |
| 03 | `soft-ui` | 柔雾靛 · 柔和界面 | light | rounded-3xl、彩色柔影、hover 上浮 |

**实现方式**：每套风格在 `themes.css` 里定义一组 CSS 自定义属性（`--tx-1`、`--bg-surface`、`--ac`、`--r-card`、`--sh-card`…），挂在 `[data-style='key']` 选择器下；外壳 `App.vue` 把 `:data-style="activeKey"` 绑在 `.app` 根节点上，`useTheme.js` 只负责切 `activeKey` 并持久化到 `localStorage`。**新写样式一律用这些语义令牌，不要写死颜色**，否则换肤会漏（唯一例外是 C74111 分档四色 `--c74-a/b/c/d`，固定不随主题变）。

**收益**：换肤不重新渲染任何组件，只是变量值变了。这也是**不引入 UI 组件库**的原因——UI 库的默认样式需要大量 `!important` 覆盖，11 套主题下会失控。

`tone` 字段让外壳知道该风格是明是暗，用来调画廊里标题字号、缩略图比例这类细节。

## 三、数据层：mock / live 双通道（`useDataSource.js`）

### 3.1 为什么要有 mock

这套界面首先是**风格演示**。如果后端没起、或者库里是空的，界面就不该白屏——否则演示价值为零。所以两条通道产出**完全相同的形状**：

```js
const dataset = computed(() => (mode.value === 'live' && liveData.value ? liveData.value : MOCK_DATASET))
```

| 通道 | 来源 | 用途 |
| --- | --- | --- |
| `mock` | `data/mock.js`（静态数据） | 演示、离线、后端异常时的兜底 |
| `live` | 后端 10 张核心表 | 真实业务使用 |

### 3.2 实时通道拉哪些表

```js
const TABLES = [
  ['customers', 'customer'],            ['projects', 'project'],
  ['persons', 'person'],                ['members', 'project_member'],
  ['coopEntities', 'coop_entity'],      ['partnerPersons', 'partner_person'],
  ['competitorPersons', 'competitor_person'], ['internalPersons', 'internal_person'],
  ['orgs', 'org'],                      ['c74111Rows', 'project_c74111'],
]
```

并行拉取后交给 `adapters.js` 装配成界面需要的数据集（关系图节点、KPI、项目列表…）。

### 3.3 失败即回落，绝不白屏

```js
try {
  // 拉 10 张表 + 装配
  mode.value = 'live'; status.value = 'ok'
} catch (e) {
  status.value = 'error'; error.value = e; mode.value = 'mock'   // ← 回落到演示数据
}
```

同时记录**每张表的实际行数**（`tableCounts`），这样用户能一眼区分「接上了但表是空的」和「根本没接上」——这两种情况的处理方式完全不同，混在一起会浪费大量排查时间。

### 3.4 数据源状态显示

`probe()` 打 `/meta/health`，拿到 `db_path` 与 `table_count` 显示在界面上。切到 live 时如果后端不在线，会先探一次再决定。

## 四、请求层（`api/client.js`）

### 4.1 Base URL 三级回退

```js
window.__BCRM_API_BASE__            // ① 打包后 Tauri 壳在页面脚本执行前注入
  ?? localStorage['bcrm.apiBase']   // ② 用户在界面上手填
  ?? 'http://127.0.0.1:8787/api/v1' // ③ 开发默认
```

① 的注入时机很关键：Tauri 的 `initialization_script` 在**页面任何脚本之前**执行，所以 `client.js` 模块求值时 `window.__BCRM_API_BASE__` 已经就位。打包后端口是随机的，因此**不需要改一行前端代码**。

### 4.2 `qs()`：把嵌套对象摊平成查询串

这是前后端语法差异的**唯一收敛点**：

| 传入 JS | 产出查询串 |
| --- | --- |
| `filter: { a: 1 }` | `filter[a]=1` |
| `filter: { a__gt: 1 }` | `filter[a__gt]=1` |
| `or: [{ a: 1, b: 2 }]` | `or[0][a]=1&or[0][b]=2` |
| `and: [{ a: 1 }, { b: 2 }]` | `and[0][a]=1&and[1][b]=2` |
| `filter: { a: [1, 2] }` | `filter[a]=1&filter[a]=2` |
| `''` / `null` / `undefined` | **跳过不发** |

最后一行很重要：把空串当 `= ''` 发出去会变成「查行业为空的客户」，与「不按行业筛选」是两回事。

## 五、元数据层（`api/meta.js`）—— 表单与筛选器的单一依据

### 5.1 元数据归一化

```js
function normalizeMeta(table, raw) { ... }
```

产出的 `columns[]` 每项带着界面需要的全部信息：`sqlType`、`primaryKey`、`autoIncrement`、`notNull`、`unique`、`enum`、`boolean`、`json`、`hasDefault`、`references`。

### 5.2 本轮修掉的一个真 bug：外键信息读错了位置

后端 `/meta/tables/{table}` 里，**列级 `references` 全是 `null`**，外键关系在**表级 `foreignKeys`**：

```json
{
  "columns": [ { "name": "customer_id", "references": null, ... } ],
  "foreignKeys": [ { "columns": ["customer_id"], "refTable": "customer", "refColumns": ["id"] } ]
}
```

而旧的 `normalizeMeta` 只读列级：

```js
references: c.references ? {...} : null      // → 永远 null
```

**后果**：表单里外键字段降级成普通文本框、表格里外键标签为空、`fkColumns` 永远为空数组 —— 外键相关的功能**从来没生效过**，但因为不报错，一直没被发现。

**修法**：在归一化时把表级 `foreignKeys` 归并回每一列：

```js
const fkByCol = {}
for (const fk of raw?.foreignKeys ?? raw?.foreign_keys ?? []) {
  for (const c of fk.columns ?? []) fkByCol[c] = { table: fk.refTable, column: (fk.refColumns ?? [])[0] ?? 'id' }
}
// 再给每列挂上 references = fkByCol[c.name] ?? 列级 references
```

### 5.3 操作符目录：按列类型收窄

前端**不自己发明操作符**，20 个操作符与后端 `query/ast.rs` 一一对应。`operatorsFor(col)` 按列类型给出**可用子集**：

| 列类型 | 可用操作符 |
| --- | --- |
| JSON 列 | `json_contains` / `json_has_all` / `json_eq` / `json_like` / `json_len_gte` / `null` / `notnull` |
| 布尔列 | `eq` / `ne` / `null` / `notnull` |
| 枚举列 | `eq` / `ne` / `in` / `nin` / `null` / `notnull` |
| 外键列 / 数值列 | `eq` / `ne` / `gt` / `gte` / `lt` / `lte` / `between` / `in` / `nin` / `null` / `notnull` |
| 文本列 | `eq` / `ne` / `like` / `nlike` / `prefix` / `suffix` / `in` / `nin` / `null` / `notnull` |

**为什么不把 20 个操作符全给用户**：对枚举列做 `like` 在语义上没有意义，而且很容易让人以为查询没生效。按类型收窄能消掉大部分误用。

同时导出三个辅助集合：`VALUELESS_OPS`（`null` / `notnull` 不需要填值）、`MULTI_OPS`（`in` / `nin` / `between` / `json_has_all` 逗号分隔多值）、`RANGE_OPS`（`between` 需要两个值）。

### 5.4 控件形态由列类型决定

```js
inputKindOf(col) → 'boolean' | 'enum' | 'fk' | 'json' | 'date' | 'number' | 'text'
```

- 枚举列 → 下拉（选项直接来自元数据的 `enum`）→ **从源头杜绝枚举非法值**
- 外键列 → 下拉（选项从父表拉，`loadFkOptions()`）
- 布尔列 → 开关
- JSON 列 → 提示「填裸元素」

### 5.5 空库自播种（`api/seed.js`）

工作台有 4 个功能（资讯 / 客户更新 / 竞品动态 / 快捷入口）得有数据才看得出效果。
`ensureWorkbenchSeed()` 在**对应表为空时**补一次，已有数据就完全不动：

| 表 | 条数 | 前置条件 |
| --- | --- | --- |
| `news_item` | 14 | 无 |
| `dashboard_shortcut` | 6 | 无 |
| `dashboard_update_log` | 1 | 无 |
| `customer_news` | 每客户 2 条 | 需要库里有 `customer` |
| `entity_history` / `entsales_confrontation` | 每竞争方 2 条 / 若干 | 需要库里有 `coop_entity` |

**三条约束**：① 只补空表，有数据不动；② 客户/竞品相关记录去读**真实的 `customer.id` / `coop_entity.id`**，
不让外键指向不存在的行；③ 资讯的 `source` 一律写「演示数据」，界面上能一眼看出不是真实抓取。
任何一步失败都**不抛错** —— 工作台照常可用，只是对应卡片为空。

> 这个机制顺带成了**打包验证的探针**：清空这几张表再启动 exe，
> 数据若原样回填，就证明「内嵌前端 → 注入的随机端口 → 内嵌后端」整条链路是通的。

## 六、数据管理页：`CrudView.vue`（本轮重头戏）

### 6.1 原状与缺口

原版只有一个**关键字输入框**（`q`，全表文本列模糊匹配）＋ 分页 ＋ 新建/编辑/删除。

而需求明确要求「查询条件包含**所有字段单独或联合查询**」——一个关键字框显然不够。所以本轮补了**条件筛选器**。

### 6.2 筛选器的状态设计

```js
const panelOpen = ref(false)
const filters = ref([])              // 编辑中的条件（可自由增删）
const filterLogic = ref('and')       // 'and' | 'or'
const appliedFilters = ref([])       // 已生效的条件快照
const appliedLogic = ref('and')      // 已生效的逻辑
```

**编辑态与生效态分离**是刻意的：改条件时列表不该抖动，只有点「应用筛选」才把 `filters` 快照到 `appliedFilters` 并重新请求。这样用户能放心地边改边想，也能一眼看到「当前结果对应的是哪组条件」。

### 6.3 三条使用路径

#### ① 表头漏斗：一键按某列筛选（对应「每个字段单独查询」）

每一列的表头右侧有一个漏斗图标，点一下即为该列生成一个过滤条件并展开面板。已在筛选中的列，漏斗高亮：

```js
const isFilteredColumn = (name) => appliedFilters.value.some((f) => f.column === name)
function filterByColumn(name) { /* 追加一个 column=name 的条件 */ }
```

默认操作符按列类型取第一个可用值；默认值**自动取当前第一行该列的值**——这样点一下就得到「有结果」的筛选，用户可以在此基础上改值。

#### ② 添加条件：列 + 操作符 + 值

`addFilter(columnName, op)` 追加一行条件。三个控件联动：

- 换列 → 操作符自动归一到该列可用的第一个（例如切到 JSON 列会自动变成 `json_contains`）
- 换操作符 → 值控件形态跟着变（`null`/`notnull` 隐藏值输入、`between` 变成区间、`enum` 变下拉）
- 值输入 → 带「离焦即生效」的轻提示

每一行都可单独删除。顶部有 AND / OR 切换：「全部满足」= AND，「任一满足」= OR。

#### ③ 全列等值（取第 1 行）：一键盘点全字段可查性

```js
function fillAllFromFirstRow() { ... }
```

用当前**数据最全的那一行**，为这张表**每一列**各生成一条等值条件。JSON 列自动换用 `json_contains`（传整段 JSON 去 `eq` 语义不同），布尔列转成 `0`/`1`。

**这个按钮的用途就是「证明这张表的每个字段都能作为查询条件」**：理论上结果必然命中那一行；如果某列筛完是 0 条，说明该列的查询链路有问题。它把「验证全字段可查」从人工点几十次变成一次点击。

### 6.4 条件编译（`buildParams`）

```js
function buildParams(list, logic) {
  const usable = list.filter((f) =>
    f.column && colOf(f.column) && (!needsValue(f.op) || normalizeFilterValue(f) !== ''))
  const kv = (f) => [f.op && f.op !== 'eq' ? `${f.column}__${f.op}` : f.column, normalizeFilterValue(f)]
  else if (logic === 'or') return { or: [Object.fromEntries(usable.map(kv))] }
  else return { filter: Object.fromEntries(usable.map(kv)) }
}
```

三个要点：

1. **`eq` 不加后缀** —— `filter[name]=x` 而不是 `filter[name__eq]=x`，和文档一致
2. **`or` 模式把全部条件塞进同一个组** `or[0][...]` → 组内 OR。这也正好验证了后端「组内 OR、组间 AND」的语义
3. **过滤掉不完整的条件**（没选列、或需要值但值为空），避免把空条件发成 `= ''`

> ⚠️ 注意**不要**把 `or` 模式编译成 `or[0][a]&or[1][b]`。按后端语义那是「(a) AND (b)」，不是 OR。这是最容易写错的一处。

### 6.5 请求串预览

面板底部实时显示即将发出的查询串：

```
GET /customer?filter[industry]=能源&filter[level__in]=P1,P2&page=1&page_size=20
```

有 `appliedQueryString` 计算属性，基于**已生效**的条件。

这个预览有两个作用：让用户看懂界面在干什么；以及让**验证脚本可以把这串原样重放一次**，证明界面拼出来的语法真的是后端能接受的那种（而不是「界面碰巧有结果，请求串只是装饰」）。

### 6.6 增删改查的其余部分

| 功能 | 实现要点 |
| --- | --- |
| 新建 / 编辑 | 弹窗表单；控件按 `inputKindOf(col)` 生成；枚举/外键走下拉；JSON 列做格式化 |
| 必填校验 | 从元数据的 `notNull && no default` 推，**不硬编码** |
| 保存 | 提交前 `toSubmit(col, value)` 按列类型转换（布尔 → 0/1，JSON → 字符串化） |
| 删除 | 前端确认 + 后端按主键删；删完刷新列表 |
| 外键标签 | `fkLabel(c, row)` 用 `loadFkOptions()` 缓存的父表数据把 id 显示成名称 |
| 列宽 | 「紧凑列宽」开关；默认只显示主键 + 前 11 个非 JSON 列，避免 43 列横向铺满 |
| 分页 | `page` / `page_size`，与后端 `total` / `page_count` 对齐 |

## 七、导航树（`nav/dataTree.js`）

62 张表在导航里**按业务分类、每张恰好出现一次**：

| 大类 | 表数 | 分组 |
| --- | --- | --- |
| 客户 | 19 | 客户档案 / 客户经营 / 商机洞察 / 客户活动 / 人员 |
| 项目 | 8 | 项目 / 人员 / 拜访行动 |
| 合作方 | 4 | 合作方 / 人员 |
| 竞争方 | 16 | 竞争方 / 销售分析（12 张） / 人员 |
| 我方组织 | 2 | 组织 / 人员 |
| 人员画像 | 6 | 多态表（`person_type` + `person_id`） |
| 工作台数据 | 7 | 计划待办 / 便签快捷 / 专注计时 / 资讯 |

**两个额外分组的理由**（原文注释里也写了）：

- **我方组织**：`org` / `internal_person` 属于奇安信自己，既不是合作方也不是竞争方，硬塞进四分类会造成语义错误
- **人员画像**：`person_form` / `person_disc` 等 6 张多态表用 `person_type` 区分对象，同时服务客户方/合作方/竞争方/我方，放任一分类下都会误导

导出 `tableLabel(name)` / `tableCategory(name)` 供面包屑和标题复用。**这份树同时也是验证脚本的表清单来源**——脚本从侧边栏读表名，而不是另调 API，确保「测的就是界面上能点到的」。

### C74111 分档（`graphData.js`）

```js
export function tierOf(score) {
  const s = Number(score)
  if (!Number.isFinite(s)) return 'd'
  if (s > 75) return 'a'          // 绝对优势 · 可承诺
  if (s >= 50) return 'b'         // 相对优势 · 可争取
  if (s >= 25) return 'c'         // 相对劣势 · 可参与
  return 'd'                      // 绝对劣势 · 不可承诺
}
```

还有一个 `none` 档：「未诊断」。**不加这一档的话，没有诊断记录的项目会被当成 0 分，界面显示「0 分 · 绝对劣势 · 不可承诺」——这是误导性的：没评过和评完得 0 分是两件事。**

## 九、数据分析驾驶舱（`AnalyticsView.vue` + `api/analytics.js`）

第三个视图（`view === 'analytics'`），把全库聚合成控制台风格的驾驶舱。

- **数据层**（`api/analytics.js`）：一次并发拉 12 张表（常量 `TABLES`），交给 `buildAnalytics(raw)` 聚合成与数据源无关的展示模型。该模块**只在这一层碰后端列名**，组件层不碰 —— 与 `adapters.js` 同一条约定。
- **双通道**：`loadAnalytics()` 是实时通道；`MOCK_ANALYTICS = buildAnalytics(deriveMock())` 是 mock 通道，两者**形状完全一致**。任何一张表失败即**整体回落** mock —— 驾驶舱最忌讳「部分图有数据、部分图空着」却不告诉用户原因。
- **口径**：`C74_BANDS`（四档 + 未诊断）、`bandOf(score)`（`>75` 才是 a 档）、`ATTITUDE_META`（⭐ / + / = / - / X）。⚠️ 客户方人员态度取 `project_member.attitude`（`person` 表无此列）。
- **图表**：`components/cockpit/` 下 5 个手绘 SVG 组件（`Donut` / `Bars` / `Columns` / `Scatter` / `Radar`）。面板带四角标记与网格底纹、数字走等宽字体；颜色 / 圆角 / 阴影 / 动效全部读 `themes.css` 语义令牌，所以 11 套风格会把驾驶舱整体重绘。
