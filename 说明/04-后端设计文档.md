# 04 · 后端设计文档

> 后端是这套系统的技术核心：**一套代码服务 62 张表**。本文解释这套通用引擎怎么设计、SQL 怎么生成、以及为什么这么切。
>
> 代码位于 `backend/`，共 13 个 Rust 文件、约 4300 行。各文件职责与行数见下方架构图。

---

## 一、问题定义

需求原话是：「验证前端能通过后端实现对 SQLite 数据库**所有表项**增删改查，查询条件包含**所有字段单独或联合查询**」。

天真解法是给每张表写一套 handler + DAO，62 张表就是 62 × 5 = 310 个端点、上万行样板代码，而且**改一次 DDL 要改一片代码**。

真正的问题是：**表结构不是代码，是数据**。所以后端的做法是——把 DDL 编译成一份元数据，让一套泛化代码消费它。

---

## 二、整体架构

```text
backend/src/
├── main.rs          独立 HTTP 服务入口（开发期用，--port / --db 参数）
├── lib.rs           对外暴露 AppState + build_app()（Tauri 壳复用它）
├── db.rs            连接管理、PRAGMA、数据库路径解析、内嵌 SCHEMA_JSON
├── schema.rs        元数据注册表（Registry）：表/列/枚举/唯一键/外键/关联
├── routes.rs        HTTP 路由 + handler + CORS
├── crud.rs          通用增删改查执行
├── value.rs         值转换（JSON ↔ SQL 绑定）
├── error.rs         统一错误类型与响应体
└── query/
    ├── mod.rs
    ├── ast.rs       WHERE 条件 AST + 编译为 SQL 片段
    ├── parse.rs     查询串 → QuerySpec（参数解析与白名单校验）
    ├── where_dsl.rs where=... 简写 DSL 解析
    └── build.rs     QuerySpec → 完整 SELECT 语句
```

### 请求生命周期

```text
HTTP 请求
   │
   ├─ axum 路由匹配：/{table} → 中间件提取 path 参数
   │
   ▼
① 白名单校验        Registry::table(name)        ← 表名不在白名单直接 40004
   │
   ▼
② 参数解析          parse::parse_query(...)      ← 列名/操作符/聚合函数逐个校验
   │                                              ← 产出 QuerySpec
   ▼
③ 条件树构建        Cond AST                     ← filter / or / and / where / POST body
   │
   ▼
④ SQL 生成          build::build_select(spec)    ← 全部用 ? 占位，值走 params 数组
   │
   ▼
⑤ 绑定与执行        rusqlite::Connection         ← 参数化执行，杜绝注入
   │
   ▼
⑥ 结果反序列化      value::sql_to_json           ← JSON 列自动 parse 成数组/对象
   │
   ▼
⑦ 统一信封          { code, message, data }
```

**关键点**：第 ①、② 步是**仅有的两道安全边界**，且都在拼 SQL 之前完成。能走到第 ④ 步的列名、操作符、函数名，一定都是白名单里的字符串字面量。第 ④ 步之后**不再有任何用户输入进入 SQL 文本**，只有绑定参数。

## 三、元数据注册表（`schema.rs`）

### 3.1 元数据从哪来

```rust
// db.rs
pub const SCHEMA_JSON: &str = include_str!("../resources/schema.json");
```

`schema.json` 是 `tools/build_api_docs.py` 从 DDL（`客户管理系统SQLite建库语句.md`）生成的，**编译期用 `include_str!` 嵌进二进制**。所以交付的 exe 自带完整表结构，首次运行就能建库，不需要任何外部 `.sql` 文件。

### 3.2 Registry 装了什么

| 数据 | 用途 |
| --- | --- |
| `Table` 列表 | 表白名单。62 张，非白名单表名一律 40004 |
| 每表的 `columns` | 列白名单、SQL 类型、是否 NOT NULL / UNIQUE / 主键 / 自增 |
| 每列的 `enum` | 枚举校验。非法值直接 40001，并回传 `expected` 数组 |
| 每列的 `boolean` / `json` 标记 | 决定值转换策略（0/1 ↔ true/false、JSON 文本 ↔ 数组） |
| `unique_keys` | 声明式唯一键，用于 upsert 判定与友好报错 |
| `foreign_keys` | 外键图，用于 `expand`（内联展开关联对象）与 `children`（级联子表） |
| `belongs_to` 关联 | `expand` 与 `select=rel.col` 的依据 |

**枚举校验放在应用层而不是只靠 DDL 的 CHECK**，理由是：SQLite 的 CHECK 报错只给一个 `CHECK constraint failed`，说不清是哪列、期望什么值。应用层校验能返回 `{field, reason, expected, actual}`，前端可以直接高亮出错的表单项。

## 四、查询编译（`query/`）

### 4.1 AST（`ast.rs`）

```rust
pub enum Op {
    Eq, Ne, Gt, Gte, Lt, Lte,
    Like, NLike, Prefix, Suffix,
    In, Nin, Between,
    IsNull, IsNotNull,
    JsonContains, JsonHasAll, JsonEq, JsonLike, JsonLenGte,
}
```

条件树：

```text
Cond::Leaf { column, op, values }     叶子
Cond::And(Vec<Cond>)                  组内 AND
Cond::Or(Vec<Cond>)                   组内 OR
Cond::Not(Box<Cond>)                  取反
```

编译时每个叶子用 `col_expr()` 把列名转成**带表限定的引用**（`` "customer"."industry" ``），既防歧义也让 `expand` 的 JOIN 里能安全引用。

### 4.2 三种入口统一到一棵树

| 入口 | 解析器 | 产出 |
| --- | --- | --- |
| `filter[a]=1&filter[b__gt]=2` | `parse.rs` | 若干 Leaf，`and_conds` 里 |
| `or[0][a]=1&or[0][b]=2` | `parse.rs` | 一个 `Cond::Or` |
| `and[N][...]` | `parse.rs` | 一个 `Cond::And` |
| `where=...` | `where_dsl.rs` | 递归下降解析成 Cond 树 |
| `POST /query` body | `parse.rs`（serde） | 直接构造 Cond 树 |
| `q=关键字` | `parse.rs` | 展开成所有文本列的 `LIKE` OR 组 |

**组内 OR、组间 AND** 的语义在 `parse.rs` 里体现得很直白：

```rust
for (_idx, items) in or_groups {
    let mut ls = Vec::new();
    for (k, v) in &items { ls.push(leaf_from_key(t, reg, k, v)?); }
    if let Some(c) = Cond::or(ls) { and_conds.push(c); }   // 组内 OR → 一个 Or 节点
}
for (_idx, items) in and_groups {
    let mut ls = Vec::new();
    for (k, v) in &items { ls.push(leaf_from_key(t, reg, k, v)?); }
    and_conds.push(Cond::And(ls));                          // 组内 AND
}
// 所有组统一 push 到同一个 vec → 组间 AND
```

### 4.3 生成 SELECT（`build.rs`）

```rust
pub fn build_select(t: &Table, reg: &Registry, spec: &QuerySpec) -> Result<SelectPlan, ApiError>
```

处理顺序：

1. **FROM**：主表 + 按 `expand` 追加 `LEFT JOIN`（依据 `belongs_to`）
2. **SELECT 列**：
   - 普通模式：不指定 `select` 就全列；指定了按需取；`select=customer.name` 会生成 `` "customer"."name" AS "customer__name" ``
   - 聚合模式：`group_by` 列 + `agg` 表达式，别名由 `agg=func(col):alias` 给定
3. **WHERE**：Cond 树编译成 SQL，条件之间用 `AND`/`OR` 拼接，**所有值进 `params`**
4. **GROUP BY**（若有）
5. **ORDER BY**：默认 `` ORDER BY "表名"."id" ASC ``；聚合时默认 `ORDER BY 1` 保证分页稳定
6. **LIMIT / OFFSET**：分页

产物是 `SelectPlan { sql, params, outputs }`，`outputs` 记录每列来源（基础列 / 关联列 / 聚合列），供第 ⑥ 步重建 JSON 结构。

### 4.4 聚合语法

| 写法 | 结果 |
| --- | --- |
| `agg=count(id):n` | `count("id") AS "n"` |
| `agg=count_distinct(industry):k` | `count(DISTINCT "industry") AS "k"` |
| `agg=sum(amount):s` / `avg` / `min` / `max` | 同名 SQL 函数 |
| `agg=count:*` | ❌ 40002，格式必须是 `func(col):alias` |

实测：

```bash
GET /project?group_by=level&agg=count(id):n
# → [{"level":"P1","n":10},{"level":"P2","n":1}]
```

### 4.5 值绑定（`value.rs`）—— 本轮修掉的一个隐蔽 bug

JSON 列在 DDL 上是 `TEXT`。所以初版直接用 `json_to_sql` 把绑定值当文本处理，结果是：

```sql
-- JSON 列存的是文本 '["a","b"]'
-- json_array_length(col) 返回 INTEGER 2
-- 但绑定参数是文本 '1'
json_array_length(col) >= '1'
```

**SQLite 的类型排序里，INTEGER/REAL 永远小于 TEXT。** 所以 `2 >= '1'` 恒为假，`json_len_gte` 任何值都查不到数据。

修法是新增一个专门给「与 `json_extract` 返回值比较」用的转换：

```rust
pub fn json_scalar_to_sql(v: &Value) -> SqlValue {
    match v {
        Value::Null => SqlValue::Null,
        Value::Bool(b) => SqlValue::Integer(if *b { 1 } else { 0 }),
        Value::Number(n) => n.as_i64().map(SqlValue::Integer)
            .or_else(|| n.as_f64().map(SqlValue::Real))
            .unwrap_or_else(|| SqlValue::Text(n.to_string())),
        Value::String(s) => SqlValue::Text(s.clone()),
        Value::Array(_) | Value::Object(_) => SqlValue::Text(serde_json::to_string(v).unwrap_or_default()),
    }
}
```

原则：**按 SQLite 的 `json_extract` 会返回什么类型来选绑定类型**，跟它对齐。`JsonLenGte` 与 `JsonEq` 都改用这个函数。

## 五、CRUD 执行（`crud.rs`）

### 5.1 创建

```text
校验列名 → 过滤出可写列（排除自增主键）→ 枚举校验 → JSON 列序列化
        → INSERT ... RETURNING * （或 last_insert_rowid + SELECT 回读）
```

**返回完整的新行**，而不是只回一个 id。这样前端不必再发一次 GET 才能刷新列表。

### 5.2 更新的两种语义

`PUT` 与 `PATCH` 走的是**同一个函数**，只差一个布尔参数：

```rust
// routes.rs
async fn put_by_id(...)   { crud::run_update(&st, &t, &body, &where_sql, params, true )? }  // full_replace
async fn patch_by_id(...) { crud::run_update(&st, &t, &body, &where_sql, params, false)? }
```

| 方法 | `full_replace` | 实现 | 风险 |
| --- | --- | --- | --- |
| `PATCH` | `false` | 只把 body 里出现的列放进 `SET`（`collect_writes(t, obj, false)`） | 安全，**推荐默认** |
| `PUT` | `true` | 先写 body 里的列，再扫一遍表结构把「没传的空列」补成 `NULL` | 会清掉没传的可空字段 |

`PATCH` 的实现要点：body 里的键**先过白名单**，再逐个 `SET "列" = ?`。空 body 直接拒绝（否则就是一条什么也不改的 UPDATE）。

`PUT` 的补 NULL 循环带四个 `continue` 守卫，这是「整体替换」不至于太危险的关键：

```rust
for c in &t.columns {
    if c.primary_key || c.auto_increment || c.not_null { continue; }   // 主键/自增/NOT NULL 不动
    if !provided.contains(&c.name) && c.default.is_none() {            // 有 DEFAULT 的也不动
        w.push((c.name.clone(), SqlValue::Null));
    }
}
```

即：**只有「可空 + 无默认值 + 本次未传」的列才会被打回 NULL**。`NOT NULL` 列和有 `DEFAULT` 的列都保留原值 —— 这比「全列覆盖」温和得多，也让 `PUT` 在 62 张宽表上不至于一碰就清空半行。

**一处刻意保留的不对称**：

| 目标 id 不存在时 | 行为 |
| --- | --- |
| `PATCH` | `updated == 0` → 返回 `404 / 40401`「记录不存在」 |
| `PUT` | 只回 `{"updated": 0}`，HTTP `200` |

`PATCH` 多这一层判空是为了让前端「改一行」时能直接拿到「这行没了」的信号；`PUT` 是幂等覆盖语义，目标不存在不视为错误。两侧都保留是有意的，但用 `PUT` 时要自己检查 `data.updated`。

另外两者都会**自动维护时间戳**：若表中有 `updated_at` / `updated_date` 且本次未显式传，`SET` 子句里追加 `"updated_at" = datetime('now','localtime')`。

### 5.3 删除的两条防呆线

```rust
// 无条件 DELETE 一律拒绝
if spec.cond.is_none() && spec.q.is_none() {
    return Err(ApiError::dangerous("无条件删除被拒绝：请提供 filter / where 条件"));
}
```

62 张表共用一个删除入口，一旦漏条件就是整表清空。所以第二道防线是 `foreign_keys=ON`：有从表引用时删除会直接失败，而不是留下孤儿数据。

### 5.4 批量

`POST/PATCH/DELETE /{table}/batch` 走**单个事务**：要么全成要么全不成。上限 1000 条（`40006`）。批量 PATCH 逐行应用各自的字段集，不是「同一组值打到所有行」。

## 六、连接与并发（`db.rs`）

| 项 | 设置 | 原因 |
| --- | --- | --- |
| 连接数 | **1** + `Mutex` | 桌面单用户，并发写入几乎为零；单连接彻底规避 SQLite 的写锁竞争 |
| `PRAGMA foreign_keys` | `ON`（**每个连接都要设**） | SQLite 默认关闭外键，且是连接级而非库级设置 |
| `journal_mode` | `WAL` | 读写不互斥，界面查询不会被写入阻塞 |
| `busy_timeout` | `5000` ms | 偶发锁等待重试 5 秒，超时返回 `50301` |
| `schema.sql` | `include_str!` 编入二进制 | 首次运行自动建库，交付零外部文件 |

> **WAL 的副作用**：库文件旁边会出现 `crm.db-wal` 和 `crm.db-shm`。**复制数据库时必须三个一起复制并保持同名**，否则可能丢掉最近未 checkpoint 的事务。这一点在交付打包时要特别注意。

### 数据库路径解析（`resolve_db_path`）

打包后按以下顺序试探，第一条成功即返回：

1. `exe 同级 / crm.db`（已存在且目录可写）
2. `exe 同级 / data / crm.db`（已存在且可写）
3. `exe 同级 / crm.db`（**不存在则建**，前提是同级目录可写）← **用户要求的默认行为**
4. `exe 同级 / data / crm.db`（同级不可写时退到子目录）
5. `%APPDATA% / Bcrm / crm.db`（最后兜底，标记为非便携模式）

「可写」通过实际写一个 `.write_probe` 文件再删除来判断，比查文件属性可靠。

## 七、CORS（`routes.rs`）

打包后界面在 `tauri://localhost`，接口在 `http://127.0.0.1:{随机端口}` —— **跨源是常态**。CORS 层放行：

- `tauri://localhost`、`http://tauri.localhost`（Tauri v2 在不同平台的来源形式）
- `http://127.0.0.1:*`、`http://localhost:*`（开发期的 Vite 5173 / preview 4173）

所以 CORS 不是开发期的临时补丁，而是**打包后的必需组件**。放行范围限定在本地回环，不对公网开放。

## 八、错误处理（`error.rs`）

### 8.1 单一错误类型

```rust
pub struct ApiError {
    pub code: u32,                  // 业务码
    pub status: StatusCode,         // HTTP 码
    pub message: String,
    pub errors: Vec<FieldError>,    // 字段级明细
    pub allowed_columns: Option<Vec<String>>,  // 白名单提示
}
```

工厂函数让调用点保持一行：`ApiError::validation("category", "取值不在枚举内")`。

### 8.2 SQLite 错误自动映射

`impl From<rusqlite::Error> for ApiError` 按 **extended_code** 分派：

| SQLite extended code | → 业务码 | HTTP |
| --- | --- | --- |
| `SQLITE_CONSTRAINT_UNIQUE` (2067) / `PRIMARYKEY` (1555) | `40901` 唯一键冲突 | 409 |
| `SQLITE_CONSTRAINT_NOTNULL` (1299) | `40001` 必填缺失 | 400 |
| `SQLITE_CONSTRAINT_CHECK` (275) | `42201` CHECK 失败 | 422 |
| `SQLITE_CONSTRAINT_FOREIGNKEY` (787) | `40008` 外键目标不存在 | 400 |
| `ErrorCode::DatabaseBusy` | `50301` 数据库忙 | 503 |
| 其它 | `50001` 数据库错误 | 500 |

**价值**：数据库层的裸错误（`UNIQUE constraint failed: customer.crm_code`）被翻译成前端能理解、能展示、甚至能高亮到字段的结构化响应。比如唯一键冲突的 `message` 会保留 SQLite 的原始约束名，直接告诉用户是**哪一列**撞了。

## 九、可测性设计

后端能在没有界面的情况下被完整验证，靠的是三条：

1. **零状态启动**：给定一个空文件路径就能建库跑起来，`tools/_verify_all_tables.mjs` 直接在隔离副本库上跑
2. **元数据可枚举**：`/meta/tables` 能列出全表，`/meta/tables/{table}` 能列出全列，所以验证脚本可以**不硬编码任何表名和列名**地遍历 62 张表 × 838 列
3. **错误结构化**：脚本能区分「后端 bug」和「我传错了」——比如 `40004 列不存在` 是脚本问题，`200 但 total=0` 才是后端问题

本轮验证规模：**8399 条断言全部通过，0 失败 0 跳过**（脚本：`tools/_verify_all_tables.mjs`，报告：`.workbuddy/verify/report.json`）。

## 十、本轮修复的两个真 bug（完整记录）

### Bug 1 · `or[N][列名]` 分组解析失败

**现象**：任何 `or[0][列名]=值` 或 `and[0][列名]=值` 都返回
`400 表 customer 上不存在列 0][id`
——分组联合查询**完全不可用**。

**根因**：`unwrap_bracket` 剥外层方括号时把尾部 `]` 一起去了：

```rust
// 输入 or[0][id]
// key.starts_with("or[") && key.ends_with(']')
// → &key[3..key.len()-1]  ==  "0][id"     ← 注意是以 '0' 开头
```

而 `parse_group_key` 旧逻辑只认「以 `[` 开头」的形态：

```rust
if let Some(stripped) = s.strip_prefix('[') { ... }   // "0][id" 不匹配
(0, s.trim_end_matches(']').trim().to_string())        // → 把 "0][id" 整个当列名
```

**修法**：不改 `unwrap_bracket`（改了会连带影响别的调用点），而是让 `parse_group_key` 识别三种形态：

```rust
fn parse_group_key(inner: &str) -> (usize, String) {
    let s = inner.trim();

    // 形态二：`0][列名`（unwrap_bracket 剥完之后的实际形态）
    if let Some(pos) = s.find("][") {
        if let Ok(idx) = s[..pos].parse::<usize>() {
            let col = s[pos + 2..].trim().trim_end_matches(']').trim();
            return (idx, col.to_string());
        }
    }

    // 形态三：`[0][列名]`（保险起见，原始形态也支持）
    if let Some(stripped) = s.strip_prefix('[') {
        if let Some(end) = stripped.find(']') {
            let idx = stripped[..end].parse::<usize>().unwrap_or(0);
            let rest = stripped[end + 1..].trim();
            let rest = rest.strip_prefix('[').unwrap_or(rest);
            let rest = rest.strip_suffix(']').unwrap_or(rest);
            return (idx, rest.trim().to_string());
        }
    }

    // 形态一：`列名`（or[列名] 无下标简写）
    (0, s.trim_end_matches(']').trim().to_string())
}
```

> 修复过程中先走错过一次：一开始去改 `unwrap_bracket` 让它保留尾部 `]`，实测无效（因为其它调用点依赖它剥掉），已回退。**结论：修在消费侧，不动共享工具函数。**

### Bug 2 · `json_len_gte` 恒不命中

见 §4.5。根因是 SQLite 类型排序（INTEGER < TEXT）配合错误的绑定类型。

### 修复后的复验

`tools/_probe_query.mjs` 逐条验证：

| 用例 | 修复前 | 修复后 |
| --- | --- | --- |
| `or[0][a]&or[0][b]` 同组 OR | 400 列不存在 | ✅ 200，total=1 |
| `or[列名]` 无下标简写 | 400 | ✅ 200，total=1 |

## 十一、设计取舍清单

| 决策 | 选择 | 放弃的方案 | 理由 |
| --- | --- | --- | --- |
| 表接入方式 | 元数据驱动通用引擎 | 每表一套 handler | 62 张表；DDL 变更只改元数据 |
| ORM | 不用 | SeaORM / Diesel | 会生成上千个结构体，而通用 CRUD 只需要「列→值」 |
| 并发 | 单连接 + Mutex | 连接池 | 桌面单用户，池化收益为零却引入锁竞争 |
| 校验位置 | 应用层 + DDL 双保险 | 只靠 DDL CHECK | 要返回 `{field, expected}` 才能让前端高亮 |
| 端口 | 打包后随机 | 固定 8787 | 用户机器上 8787 可能被占用 |
| 后端形态 | 编进 Tauri 进程 | sidecar 双 exe | 单文件交付，无残留进程、无时序协商 |
| SQL 构建 | 全参数化 + 白名单 | 字符串拼接 | 安全边界放在拼 SQL 之前 |
| 删表保护 | 拒绝无条件 DELETE | 依赖前端确认 | 62 张表共用入口，防呆必须在后端 |
