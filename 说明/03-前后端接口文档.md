# 03 · 前后端接口文档

> 本文所有请求/响应示例都**实测过**（跑在 `127.0.0.1:8899` 的隔离副本库上），不是从代码推演的。
>
> 逐表字段级说明（838 列的完整清单）见仓库根目录的 `客户管理系统API接口文档.md`；本文讲的是**通用规则**，任何一张表都适用。

---

## 一、核心约定

| 项 | 值 |
| --- | --- |
| Base URL（开发） | `http://127.0.0.1:8787/api/v1` |
| Base URL（打包后） | `http://127.0.0.1:{系统随机端口}/api/v1`，端口由壳注入 `window.__BCRM_API_BASE__` |
| **资源路径** | **就是表名本身**，`/api/v1/customer`、`/api/v1/project_c74111`。**不做驼峰转换、不加复数、不加前缀** |
| **参数名** | **就是列名**，`filter[crm_code]=S003` |
| 请求头 | 写操作需 `Content-Type: application/json` |
| 成功判定 | HTTP 200/201 **且** `code === 0` |
| 表数量 | **62 张**，全部零配置接入通用路由 |

### 为什么路径用裸表名

62 张表的表名已经是业务语义（`customer_budget_detail`、`competitor_person_project_rel`），再加一层 REST 风格的资源改名只会制造映射表和心智负担。**表名是唯一标识，接口路径就直接用它**——前端从元数据拿到表名，就能拼出请求，不需要维护第二份映射。

## 二、统一响应体

### 2.1 成功

```json
{ "code": 0, "message": "ok", "data": { ... } }
```

信封只有三个键：`code` / `message` / `data`（`data` 为空时是 `null`）。

### 2.2 失败

```json
{
  "code": 40001,
  "message": "字段校验失败",
  "data": null,
  "errors": [{ "field": "category", "reason": "取值不在枚举内", "expected": ["主客户","关联客户"], "actual": "大客户" }]
}
```

未知表名/列名时额外带 `allowed_columns`，前端可据此做「你是不是想写……」的提示：

```json
{ "code": 40004, "message": "表 customer 上不存在列 nosuchcol", "data": null, "allowed_columns": ["id","crm_code","name", ...] }
```

### 2.3 `data` 的形状取决于端点

| 端点 | `data` 形状 |
| --- | --- |
| `GET /{table}`（列表） | `{ items: [...], page, page_size, total, page_count }` |
| `GET /{table}/{id}`（详情） | 单个对象 `{ id: 3, crm_code: "S003", ... }` |
| `GET /{table}/count` | `{ count: 11 }` |
| `GET /{table}/exists` | `{ exists: true }` |
| `POST /{table}`（新增） | 新建出的完整行 |
| `PATCH/PUT /{table}/{id}` | 更新后的完整行 |
| `DELETE ...` | `{ deleted: n }` |
| `GET /{table}/export` | **不是 JSON**，是 `text/csv` |

## 三、路由总表（62 张表通用）

| 路径 | 方法 | 作用 |
| --- | --- | --- |
| `/meta/tables` | GET | 按业务分组返回表清单 |
| `/meta/tables/{table}` | GET | 单表元数据：列/类型/枚举/唯一键/外键/默认值 |
| `/meta/enums` | GET | 全库 44 组枚举字典 |
| `/meta/schema` | GET | 完整 schema |
| `/meta/health` | GET | 健康检查：库路径、表数、各表行数 |
| `/{table}` | GET | **列表查询**（支持全部查询语法） |
| `/{table}` | POST | **新增**一行 |
| `/{table}` | DELETE | **按条件删除**（必须带条件，见 §7.3） |
| `/{table}/count` | GET | 计数（条件同列表） |
| `/{table}/exists` | GET | 存在性（条件同列表） |
| `/{table}/by` | GET | 按键查：`?crm_code=S003`，含完整唯一键时返回单对象 |
| `/{table}/batch` | POST | 批量新增（≤1000 条） |
| `/{table}/batch` | PATCH | 批量更新 |
| `/{table}/batch` | DELETE | 批量删除 |
| `/{table}/query` | POST | **条件树查询**（复杂嵌套 AND/OR） |
| `/{table}/upsert` | POST | 存在则更新、不存在则新增 |
| `/{table}/export` | GET | 导出 CSV |
| `/{table}/{id}` | GET / PUT / PATCH / DELETE | 按主键查 / 整体替换 / 局部更新 / 删除 |
| `/{table}/{column}/{value}` | GET | 按键查（路径形式） |
| `/{table}/{id}/children/{child}` | GET / PUT | 级联子表：读某主表的从表 / 整体替换从表 |

> **参数名冲突提醒**：`/{table}/{column}/{value}` 与 `/{table}/{id}` 共用两段路径。后端按「第二段是否为纯数字」以及列名白名单来区分，实际使用中请优先用 `/by` 或 `filter` 形式，语义更明确。

## 四、列表查询完整参数

`GET /api/v1/{table}` 支持的**全部**参数（来自后端 `QuerySpec`）：

| 参数 | 形式 | 说明 |
| --- | --- | --- |
| `filter[列名]` | `filter[industry]=能源` | 等值 |
| `filter[列名__操作符]` | `filter[amount__gt]=100` | 带操作符，见 §5 |
| `filter[列名]`（同名多次） | `filter[id]=1&filter[id]=2` | **聚合为 IN 语义**，见下方警告 |
| `logic` | `logic=or` | 把整层 `filter` 从 AND 改为 OR |
| `or[组号][列名]` | `or[0][industry]=能源` | OR 分组 |
| `and[组号][列名]` | `and[0][a]=1` | AND 分组 |
| `where` | `where=id=3` | 简写 DSL |
| `q` | `q=能源` | 全表文本列模糊匹配 |
| `select` | `select=id,name` | 只返回指定列；也支持 `select=customer.name`（需配合 `expand`） |
| `order_by` | `order_by=id:desc` | 可多值，`列名:asc\|desc` |
| `page` / `page_size` | `page=2&page_size=20` | 默认 1 页 / 20 条，**上限 200** |
| `limit` / `offset` | `limit=2&offset=0` | 与分页二选一 |
| `group_by` | `group_by=level` | 分组 |
| `agg` | `agg=count(id):n` | 聚合，格式 `func(列):别名`，可多值 |
| `expand` | `expand=customer` | 内联展开 belongs-to 关联对象 |
| `children` | `children=project` | 内联展开子表 |
| `distinct` | `distinct=1` | SELECT DISTINCT |
| `count_only` | `count_only=1` | 只回 `total`，`items` 为空 |
| `raw` | `raw=1` | JSON 列保持原始文本，不做反序列化 |

> ⚠️ **同名参数是 IN 不是 AND**：`filter[id]=1&filter[id]=2` 会被聚合成 `id IN (1,2)`。
> 如果你想要 `AND` 语义，**必须换不同的列**，或者用 `and[0][...]&and[1][...]`。
> 这个坑在写验证脚本时踩过：用 `filter[a]=真&filter[a]=假` 做「AND 反证」会得到「查得到」的假象。

### 实测示例

```bash
# 分组聚合
GET /project?group_by=level&agg=count(id):n
# → data.items = [{"level":"P1","n":10},{"level":"P2","n":1}]

# 展开关联客户
GET /project?expand=customer&page_size=1
# → items[0].customer = { "crm_code": "...", "name": "...", ... }

# 只取两列 + 倒序
GET /project?select=id,name,level&order_by=id:desc&page_size=2
# → items = [{"id":33,...},{"id":32,...}]

# 按键查（用唯一键）
GET /customer/by?crm_code=S003
# → data = { "id":3, "crm_code":"S003", "industry":"能源", ... }   ← 单个对象，不是数组

# 子表
GET /customer/3/children/project?page_size=2
# → items = [...]   （customer_id=3 的项目）

# 导出 CSV
GET /customer/export?filter[id]=3&select=id,industry
# → Content-Type: text/csv
#   id,industry
#   3,能源
```

## 五、查询操作符（20 个）

语法：`filter[<列名>__<操作符>]=<值>`。不写操作符 = `eq`。

| 操作符 | 别名 | 含义 | 示例 | 编译为 |
| --- | --- | --- | --- | --- |
| `eq` | — | 等于 | `filter[level]=P1` | `level = ?` |
| `ne` | `not` | 不等于 | `filter[level__ne]=P4` | `level <> ?` |
| `gt` | — | 大于 | `filter[amount__gt]=100` | `amount > ?` |
| `gte` | `ge` | 大于等于 | `filter[amount__gte]=100` | `amount >= ?` |
| `lt` | — | 小于 | `filter[gross_margin__lt]=20` | `gross_margin < ?` |
| `lte` | `le` | 小于等于 | `filter[due_time__lte]=2026-09-30` | `due_time <= ?` |
| `like` | — | 包含 | `filter[name__like]=银行` | `name LIKE '%' \|\| ? \|\| '%'` |
| `nlike` | — | 不包含 | `filter[name__nlike]=测试` | `NOT LIKE` |
| `prefix` | — | 前缀 | `filter[crm_code__prefix]=C00` | `LIKE ? \|\| '%'` |
| `suffix` | — | 后缀 | `filter[email__suffix]=@abc.com` | `LIKE '%' \|\| ?` |
| `in` | — | 命中集合 | `filter[level__in]=P1,P2` | `IN (?,?)` |
| `nin` | — | 不在集合 | `filter[info_type__nin]=线索` | `NOT IN (?)` |
| `between` | — | 闭区间 | `filter[year__between]=2023,2026` 或 `2023~2026` | `BETWEEN ? AND ?` |
| `null` | `isnull` | 为空 | `filter[remark__null]=1` | `IS NULL` |
| `notnull` | `isnotnull` | 非空 | `filter[contact__notnull]=1` | `IS NOT NULL` |
| `json_contains` | — | JSON 数组含**任一** | `filter[key_scenes__json_contains]=数据中台` | `EXISTS(json_each(...))` |
| `json_has_all` | — | JSON 数组含**全部** | `filter[key_scenes__json_has_all]=A,B` | 多个 `json_each` AND |
| `json_eq` | — | JSON 内部等值 | `filter[p3p4_flags.p1__json_eq]=1` | `json_extract(col,'$.p1') = ?` |
| `json_like` | — | JSON 内部模糊 | `filter[market_share__json_like]=金融` | 对全部值匹配 |
| `json_len_gte` | — | JSON 数组长度 ≥ | `filter[key_scenes__json_len_gte]=2` | `json_array_length(col) >= ?` |

### 三条实测要点

1. **`json_contains` 要传裸元素，不要传 JSON 串**
   `filter[key_scenes__json_contains]=数据中台` ✅
   `filter[key_scenes__json_contains]="数据中台"` ❌（会把引号当值的一部分）
2. **`json_*` 操作符只能用在 JSON 列上**，用在普通列上会得到明确的 400：
   ```json
   {"code":40001,"errors":[{"field":"id","reason":"该列不是 JSON 列，不能使用 json_* 操作符"}]}
   ```
3. **`in` / `nin` 以逗号分隔**。值本身含逗号时改用 `POST /{table}/query` 传数组。

## 六、逻辑组合：AND / OR

### 6.1 语义规则（重要）

> **组内默认 OR，组间默认 AND。**

| 写法 | 语义 |
| --- | --- |
| `filter[a]=x&filter[b]=y` | `a = x AND b = y` |
| `or[0][a]=x&or[0][b]=y` | `(a = x OR b = y)` |
| `or[0][a]=x&or[1][b]=y` | `(a = x) AND (b = y)` |
| `or[a]=x`（无下标） | 等价于 `or[0][a]=x` |
| `and[0][a]=x&and[0][b]=y` | `(a = x AND b = y)` |
| `logic=or&filter[a]=x&filter[b]=y` | `(a = x OR b = y)` |

**`or[组号][列名]` 的组号是「一组内的多个条件」，组与组之间是 AND。** 这是最容易被误读的一点：
`or[0][...]` + `or[1][...]` 不是「更多 OR」，而是「一个 OR 组 AND 另一个 OR 组」。

### 6.2 实测

```bash
# 同组 OR
GET /customer?or[0][industry]=能源&or[0][level]=大型
# → WHERE (industry = ? OR level = ?)

# 组间 AND（filter + or 混合）
GET /project?filter[customer_id]=5&or[0][level]=P1&or[0][level]=P2
# → WHERE customer_id = ? AND (level = ? OR level = ?)

# 整层 OR
GET /customer?logic=or&filter[industry]=能源&filter[level]=大型
# → WHERE (industry = ? OR level = ?)
```

### 6.3 `POST /{table}/query` 条件树

复杂嵌套（多层 AND/OR、`NOT`）走这个入口，请求体是**条件树**：

- 叶子节点：`{ "column": "列名", "op": "操作符", "value": 值 }`
- 逻辑节点：`{ "op": "and" | "or" | "not", "conditions": [ ... ] }`

```http
POST /api/v1/customer/query
Content-Type: application/json

{
  "where": {
    "op": "and",
    "conditions": [
      { "column": "industry", "op": "eq", "value": "能源" },
      { "column": "id", "op": "gt", "value": 0 },
      {
        "op": "or",
        "conditions": [
          { "column": "level", "op": "eq", "value": "P1" },
          { "column": "level", "op": "eq", "value": "P2" }
        ]
      }
    ]
  },
  "select": ["id", "industry"],
  "page_size": 3
}
```

`where` 直接给数组时视为 AND：

```json
{ "where": [ { "column": "id", "op": "gt", "value": 0 } ] }
```

**常见错误**：把 `where` 写成 `{"and":[{列名:值}]}`。
后端会明确报错：`{"code":40001,"errors":[{"field":"","reason":"叶子条件缺少 column"}]}`。
正确的键名是 `conditions`，且叶子必须有 `column`。

## 七、写操作

### 7.1 新增

```http
POST /api/v1/customer
Content-Type: application/json

{ "crm_code": "C20260915", "name": "某某集团", "category": "主客户", "key_scenes": ["数据中台","安全运营"] }
```

- 成功返回 **201** + 完整行（含自增 `id`）
- `key_scenes` 这类 JSON 列可以直接传数组，后端负责序列化

**错误响应**：

| 场景 | code | HTTP |
| --- | --- | --- |
| 必填缺失 | 40001 | 400 |
| 枚举值非法 | 40001 | 400（带 `expected`） |
| JSON 列内容非法 | 40003 | 400 |
| 外键目标不存在 | 40008 | 400 |
| 唯一键冲突 | 40901 | 409 |
| CHECK 约束失败 | 42201 | 422 |

### 7.2 更新：优先用 PATCH

| 方法 | 语义 | 什么时候用 |
| --- | --- | --- |
| `PATCH /{table}/{id}` | **局部更新**，只改传了的字段 | **默认选它** |
| `PUT /{table}/{id}` | **整体替换**，未传的可空列置 NULL | 只在确实想重置整行时用 |

```http
PATCH /api/v1/customer/3
{ "industry": "金融", "level": "TOP1000大客户" }
```

**两者共有的行为**（无论 PATCH 还是 PUT）：

- 请求体必须能解析成 JSON 对象，否则 400；
- 写集合为空（一个可写字段都没传）→ `400` + `没有可更新的字段`；
- 表里如果有 `updated_at` / `updated_date` 且本次没显式传，后端自动写成 `datetime('now','localtime')`；
- 响应体是 `{"code":0,"data":{"updated":<影响行数>}}`。

**PUT 的「整体替换」到底重置了什么**（`crud.rs::run_update(full_replace=true)`）：

| 列的类型 | PUT 时未传会怎样 |
| --- | --- |
| 主键 / 自增列 | **跳过**，不受影响 |
| `NOT NULL` 列 | **跳过**，保留原值 |
| 有 `DEFAULT` 的列 | **跳过**，不动 |
| 其余可空列 | **置 NULL** ← 这就是「整体替换」的实际含义 |

也就是说 PUT **不会**把 `NOT NULL` 或有默认值的列打回默认 —— 它只清掉「既可以空、又没给默认值」的那些列。想用 PUT 清空字段前，先确认目标列是可空的。

> **一处不对称，用的时候记一下**：
>
> | 场景 | `PATCH` | `PUT` |
> | --- | --- | --- |
> | 目标 id 不存在 | `404` / `40401` 记录不存在 | **`200`**，`data.updated = 0` |
>
> `PATCH` 会检查影响行数，命中 0 行就报 404；`PUT` 只返回影响行数、不判空。
> 所以「改一行但不确定它还在不在」时用 `PATCH`，能直接拿到 404 信号；
> 用 `PUT` 就得自己看 `data.updated` 是不是 0。

### 7.3 删除

- `DELETE /{table}/{id}` —— 按主键删
- `DELETE /{table}` —— 按条件删，**必须带条件**

```bash
DELETE /api/v1/customer
# → HTTP 400  {"code":40005,"message":"无条件删除被拒绝：请提供 filter / where 条件"}
```

这是一道**防呆闸门**：62 张表共用一个删除入口，一旦漏了条件就是整表清空。

### 7.4 批量（上限 1000）

```http
POST  /api/v1/customer/batch   { "items": [ {...}, {...} ] }
PATCH /api/v1/customer/batch   { "items": [ { "id": 1, "industry": "金融" }, ... ] }
DELETE /api/v1/customer/batch  { "ids": [1, 2, 3] }
```

`page_size` 上限 200，批量上限 1000。

### 7.5 upsert

```http
POST /api/v1/project_c74111/upsert
{ "project_id": 11, "c1_score": 10, "total_score": 82 }
```

按唯一键判断：命中则更新，未命中则插入。**`project_c74111` 的 `project_id` 是 UNIQUE**，所以这个接口天然是「保存项目诊断」的写法。

## 八、元数据接口（前端表单的数据来源）

### 8.1 `GET /meta/tables/{table}`

```json
{
  "code": 0,
  "data": {
    "table": "customer",
    "group": "客户域",
    "columns": [
      { "name": "crm_code", "sqlType": "TEXT", "notNull": true, "unique": true,
        "enum": null, "boolean": false, "json": false, "primaryKey": false,
        "autoIncrement": false, "default": null,
        "references": null },
      { "name": "category", "sqlType": "TEXT", "enum": ["主客户","关联客户"], "notNull": true, ... }
    ],
    "primaryKey": ["id"],
    "uniqueKeys": [["crm_code"]],
    "foreignKeys": [
      { "columns": ["customer_id"], "refTable": "customer", "refColumns": ["id"], "onDelete": "CASCADE" }
    ]
  }
}
```

> ⚠️ **外键信息在表级 `foreignKeys`，列级 `references` 全是 `null`。**
> 这是本轮验证时发现并修掉的一个**真前端 bug**：`frontend/src/api/meta.js` 原来只读列级 `references`，导致外键下拉框和表格里的外键标签**从来没生效过**。修法是在 `normalizeMeta()` 里把表级 `foreignKeys` 归并回每一列。

### 8.2 `GET /meta/enums`

全库 44 组枚举字典，键是语义名（不是列名）：

```json
{ "category": ["主客户","关联客户"], "attitude": ["+","-","=","X","⭐"], "person_type": ["customer","partner","competitor","internal"], ... }
```

前端筛选器的「值」控件据此渲染成下拉，而不是让用户自由输入——**这样能避免绝大多数 40001 枚举错误**。

### 8.3 `GET /meta/health`

```json
{ "code": 0, "data": {
  "db_path": "./data/crm.db",
  "status": "ok",
  "table_count": 62,
  "tables": [ { "table": "customer", "rows": 11 }, ... ],
  "total_rows": 141
} }
```

界面右上角的数据源状态灯、以及「哪张表有数据 / 哪张是空的」判断都用它。

## 九、错误码手册

| code | HTTP | 含义 | 触发场景 |
| --- | --- | --- | --- |
| `40001` | 400 | 字段校验失败 | 必填缺失、枚举非法、类型不符、操作符与列类型不匹配 |
| `40002` | 400 | 参数格式错误 | 聚合表达式格式不对（应为 `func(col):alias`）、分页参数非数字 |
| `40003` | 400 | JSON 列内容非法 | 往 JSON 列写了非法 JSON |
| `40004` | 400 | 未知表名/列名/操作符 | 拼错表名或列名；响应带 `allowed_columns` |
| `40005` | 400 | 危险操作被拒 | 无条件 DELETE |
| `40006` | 400 | 超出上限 | 批量 > 1000 条、`page_size` > 200 |
| `40008` | 400 | 外键目标不存在 | 引用了不存在的父行（`PRAGMA foreign_keys=ON`） |
| `40401` | 404 | 记录不存在 | 按 id 查不到 |
| `40901` | 409 | 唯一键冲突 | 违反 UNIQUE 约束，`message` 里带 SQLite 原始约束名 |
| `42201` | 422 | CHECK 约束失败 | 枚举列 CHECK 未通过（一般先被 40001 拦住） |
| `50001` | 500 | 数据库错误 | 其余 SQLite 错误 |
| `50002` | 500 | 内部错误 | 序列化/逻辑异常 |
| `50301` | 503 | 数据库忙 | `SQLITE_BUSY`，`busy_timeout` 用尽 |

`40001` 的 `errors[]` 结构：

```json
{ "field": "category", "reason": "取值不在枚举内", "expected": ["主客户","关联客户"], "actual": "大客户" }
```

前端 `CrudView` 直接用它定位表单字段并高亮——不用再猜是哪一列填错了。

## 十、前端调用约定（`frontend/src/api/client.js`）

```js
import { api } from '@/api/client'

// 列表 + 条件
await api.list('customer', {
  page: 1, page_size: 20, order_by: 'id:desc',
  filter: { industry: '能源', level__in: 'P1,P2' },
  or: [{ industry: '能源', level: '大型' }],   // → or[0][industry]=...&or[0][level]=...
  logic: 'and',
})
```

`qs()` 负责把嵌套对象摊平成查询串：

| 传入 | 产出 |
| --- | --- |
| `filter: { a: 1 }` | `filter[a]=1` |
| `filter: { a__gt: 1 }` | `filter[a__gt]=1` |
| `or: [{ a: 1, b: 2 }]` | `or[0][a]=1&or[0][b]=2` |
| `and: [{ a: 1 }, { b: 2 }]` | `and[0][a]=1&and[1][b]=2` |
| 数组值 `filter: { a: [1,2] }` | `filter[a]=1&filter[a]=2`（后端聚合为 IN） |
| 空串 / null / undefined | **跳过不发**（避免把空条件当 `= ''` 查询） |

Base URL 解析优先级：

```js
window.__BCRM_API_BASE__   // ① 打包后由 Tauri 壳注入（随机端口）
  ?? localStorage['bcrm.apiBase']   // ② 用户在界面上手填的
  ?? 'http://127.0.0.1:8787/api/v1' // ③ 开发默认
```

## 十一、本轮验证发现并修复的接口问题

| # | 问题 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | `or[0][列名]` / `and[0][列名]` **一律报「表 X 上不存在列 0][列名」** | 参数解析剥外层方括号后得到 `0][列名`，旧逻辑只认以 `[` 开头的形态，于是把整串当列名 | 重写 `parse_group_key`，识别 `列名` / `0][列名` / `[0][列名]` 三种形态（`backend/src/query/parse.rs`） |
| 2 | `json_len_gte` **任何值都查不到数据** | JSON 列在 DDL 上是 `TEXT`，绑定值时把数字 `1` 转成了文本 `"1"`；SQLite 类型排序里 INTEGER/REAL **永远小于** TEXT，`json_array_length(...) >= '1'` 恒为假 | 新增 `value::json_scalar_to_sql`，按 `json_extract` 的实际返回类型选绑定类型；`JsonLenGte` 与 `JsonEq` 改用它（`backend/src/value.rs` + `query/ast.rs`） |

两条都通过 8399 条后端断言 + 界面端全表逐列扫描复验。
