# 01 · 环境准备与打包指南

> 目标：在一台干净的 Windows 机器上，从源码构建出可交付程序 —— `Application/bcrm-desktop.exe`（Tauri 单文件）、`Application/BCRM客户管理系统_1.0.0_x64-setup.exe`（NSIS 安装包，含 WebView2 离线捆绑）、以及 `EXE/`（前后端分离便携版）。
>
> 本文的所有版本号与路径都来自**本项目的实际构建机**，可直接照抄。

---

## 一、需要装什么（总览）

| 组件 | 用途 | 本项目实测版本 | 是否必须 |
| --- | --- | --- | --- |
| **Rust 工具链（MSVC 目标）** | 编译后端 axum 服务与 Tauri 桌面壳 | `rustc 1.98.1` / `cargo 1.98.1`，工具链 `stable-x86_64-pc-windows-msvc` | ✅ 必须 |
| **Visual Studio 2022 生成工具（含 VC++）** | Rust 的 MSVC 链接器（`link.exe`）与 Windows 头文件 | VS 2022 Community，Windows SDK `10.0.26100.0` | ✅ 必须 |
| **Node.js** | 构建前端（Vite），以及运行验证脚本 | `v24.21.0` | ✅ 必须 |
| **WebView2 运行时** | Tauri 用它渲染界面 | Windows 11 / 较新 Win10 已内置 | ⚠️ 运行期需要，Win11 免装 |
| **Python 3** | 仅用于从 DDL 重新生成元数据/文档 | `3.13.14` | ❌ 可选 |
| **Tauri CLI** | 打 NSIS 安装包（`cargo tauri build`） | `cargo install tauri-cli --version "^2"`（v2.11.4） | ⚠️ 仅打安装包时需要；只要单文件 exe 则 `cargo build` 足够 |

> **单文件 exe 不需要 CLI**：Tauri v2 会把前端产物**编进二进制**，所以 `cargo build --release` 出来的 `bcrm-desktop.exe` 本身就是完整可执行程序。
> **只有要打 NSIS 安装包**（自带开始菜单/桌面快捷方式、离线捆绑 WebView2）时，才需要 `cargo install tauri-cli --version "^2"`，然后用 `cargo tauri build`（注意：它**不接收 `--manifest-path`**，必须先 `cd launcher`）。

## 二、逐步安装

### 2.1 Rust（MSVC 目标）

```powershell
winget install Rustlang.Rustup
# 装完重开终端，确认目标是 MSVC 而不是 GNU
rustup default stable-x86_64-pc-windows-msvc
rustc -Vv      # 期望看到 host: x86_64-pc-windows-msvc
cargo -V
```

**关键点**：必须是 `-pc-windows-msvc`。用 `-gnu` 会导致 Tauri 依赖（`windows` / `webview2-com`）编译失败。

### 2.2 Visual Studio 2022 生成工具（MSVC）

```powershell
winget install Microsoft.VisualStudio.2022.BuildTools
```

在安装器里勾选 **「使用 C++ 的桌面开发」** 工作负载（组件 ID：`Microsoft.VisualStudio.Component.VC.Tools.x86.x64`）。它会一并装上 Windows SDK。

验证：

```powershell
& "C:\Program Files (x86)\Microsoft Visual Studio\Installer\vswhere.exe" `
  -latest -products * -requires Microsoft.VisualStudio.Component.VC.Tools.x86.x64 `
  -property installationPath
# 应输出类似 C:\Program Files\Microsoft Visual Studio\2022\Community
```

> **注意**：`link.exe` 通常**不在**全局 `PATH` 里，`where link` 找不到是正常的。`cargo` 会通过 `vswhere` 自行定位。只要上面这条命令能输出路径就没问题。

### 2.3 Node.js

```powershell
winget install OpenJS.NodeJS.LTS     # 或装 24.x
node -v                              # v24.21.0
```

### 2.4 WebView2 运行时（仅运行期）

Windows 11 与 Windows 10 21H2 之后已内置，无需安装。
若目标机器是更老的 Win10：

```powershell
winget install Microsoft.EdgeWebView2Runtime
# 或从 https://developer.microsoft.com/microsoft-edge/webview2/ 下载 Evergreen Bootstrapper
```

判断方法：双击 exe 后如果**进程在但窗口不出现**，看 `bcrm-launcher.log`；若日志里出现创建窗口失败，就是缺 WebView2。

## 三、开发态：前后端分开跑（推荐日常开发用）

打包成单 exe 每次都要编译 Rust，太慢。日常改动优先用这套：**后端独立进程 + Vite 热更新**。

### 3.1 启动后端（一次编译，可反复重启）

```bash
cd backend
cargo run -- --port 8787 --db ../data/crm.db
```

启动后自检：

```bash
curl http://127.0.0.1:8787/api/v1/meta/health
# {"code":0,...,"data":{"db_path":"../data/crm.db","status":"ok","table_count":62,...}}
```

**数据库路径规则**：`--db` 指向哪个文件就用哪个，不存在会自动建库（表结构内嵌在二进制里，来自 `backend/resources/schema.sql`）。开发期建议固定用 `data/crm.db`，与交付目录里的 `crm.db`（`Application/` 或 `EXE/`）分开，避免误动交付库。

### 3.2 启动前端

```bash
cd frontend
npm install          # 首次
npm run dev          # http://127.0.0.1:5173
```

Vite 的 `server.proxy` 已把 `/api` 转发到 `127.0.0.1:8787`，所以前端不必配 CORS 也能联调。
界面右上角可切换数据源：**演示数据（mock）** ↔ **实时数据（live）**。切到实时且后端在线时，状态栏会显示实际数据库路径与行数。

### 3.3 生产态预览（构建产物）

```bash
cd frontend
npm run build        # 产出 frontend/dist
npm run preview      # http://127.0.0.1:4173
```

预览模式下不走 Vite 代理，前端会直接请求 `http://127.0.0.1:8787/api/v1`（后端 CORS 已放行 4173 源）。

## 四、打包成单 exe（交付用）

### 4.1 一条命令

```bash
cd frontend && npm run build              # ① 先出前端产物，必须在前
cd ../launcher && cargo build --release   # ② 编桌面壳 + 内嵌后端（单文件 exe）
# 可选：打 NSIS 安装包（需先 cargo install tauri-cli --version "^2"）
cd ../launcher && cargo tauri build       # ③ → bundle/nsis/*.exe
```

产出：

- 单文件：`launcher/target/release/bcrm-desktop.exe`
- 安装包：`launcher/target/release/bundle/nsis/BCRM客户管理系统_1.0.0_x64-setup.exe`（约 208 MB，含 WebView2 离线安装器）

**① 必须在 ② 之前**。`launcher/build.rs` 里注册了 `cargo:rerun-if-changed=../frontend/dist`，但它只能**触发重编**，没法替你先把前端构建出来。如果 `dist/` 不存在或过期，exe 里嵌的就是旧界面 —— 这种「改了前端但 exe 没变」的现象最难排查，务必按顺序来。

### 4.2 组装交付目录

```bash
mkdir -p Application
cp launcher/target/release/bcrm-desktop.exe Application/bcrm-desktop.exe
cp "launcher/target/release/bundle/nsis/BCRM客户管理系统_1.0.0_x64-setup.exe" Application/
```

目录结构：

```text
Application/
├── bcrm-desktop.exe                        ← 双击这个（单文件便携版）
├── BCRM客户管理系统_1.0.0_x64-setup.exe     ← 安装包（含 WebView2 离线捆绑）
├── 修复启动.bat                            ← 「双击打不开」时双击它（见 4.7）
├── 使用说明.txt
├── crm.db                                  ← 运行时自动生成（与 exe 同级）
├── crm.db-wal / crm.db-shm                 ← 运行时自动生成（WAL 模式）
└── bcrm-launcher.log / -error.log          ← 运行时自动生成，排查用

EXE/                                       ← 前后端分离便携版（可选形态）
├── bcrm-server.exe                         ← 后端（监听 127.0.0.1:8787）
├── index.html + assets/                    ← 前端静态文件
├── start.bat                               ← 一键起后端 + 开页面
└── 启动说明.txt
```

> 数据库与 exe 同级是**默认规则**；若该目录不可写，会自动回退到 `%LOCALAPPDATA%\Bcrm\crm.db`（见 4.7 与第五节）。

### 4.3 首次运行

双击 exe。程序启动流程：

1. 定位数据库 → 同级 `crm.db` 不存在就按内嵌 DDL **自动建库**；
2. 后端在 `127.0.0.1` 上**随机空闲端口**启动；
3. 把该端口注入页面，窗口打开。

因此 `Application/` 里**不必预置 crm.db**，直接双击就能得到一套完整可用的空库。若要带上演示数据，把准备好的 `crm.db` 拷进 `Application/`（或 exe 同级）即可（**WAL 模式下如果库正在被写，务必连 `crm.db-wal` 一起复制**，否则可能丢最近的事务）。

> **「空库」其实不是全空**，两处会自动补内容：
>
> | 来源 | 补什么 | 时机 |
> | --- | --- | --- |
> | `schema.sql` 末尾的内嵌 INSERT | `org` 里的组织根节点「奇安信集团」（`level=0`） | 建库时 |
> | 前端 `api/seed.js` 的 `ensureWorkbenchSeed()` | `news_item`（14 条行业议题）、`dashboard_shortcut`（6 个真实站点）、`dashboard_update_log`；客户的 `customer_news`、竞品的 `entity_history` / `entsales_confrontation`（这两项需要有真实 `customer` / `coop_entity` 行才会补） | 首次打开工作台时 |
>
> 前端这份补种**只在对应表为空时执行一次**，已经有数据就完全不动。资讯的 `source` 一律写成「演示数据」，界面上能一眼看出不是真实抓取 —— 测布局、看卡片效果时不用先手工造数据。

### 4.4 为什么端口是随机的

开发期固定 8787，但用户机器上 8787 完全可能被别的程序占用。所以打包后 `bind("127.0.0.1:0")` 让系统分配空闲端口，再由 `initialization_script` 注入成 `window.__BCRM_API_BASE__`，前端 `api/client.js` 优先读它。**打包后不需要改一行前端代码。**

### 4.5 一个必须记住的坑：`from_std` 要在运行时上下文里调用

`launcher/src/main.rs` 里把已经 bind 好的 std listener 交给 axum 用，中间要经过 `tokio::net::TcpListener::from_std`。**这个函数必须在 Tokio 运行时上下文内调用**，而 Tauri 的 `.setup(|app| ...)` 回调跑在主线程、**并不在那个运行时里**。

在 `setup` 里直接调用会 panic：

```text
thread 'main' panicked at src\main.rs:99:28:
there is no reactor running, must be called from the context of a Tokio 1.x runtime
```

**症状极具迷惑性**（本轮实际踩过）：

| 观察到的现象 | 真实原因 |
| --- | --- |
| 双击 exe 一闪而过 | 进程在 setup 阶段 panic 退出 |
| `bcrm-launcher.log` 只写到「API 地址」就没了，**没有「窗口已创建」** | panic 发生在建窗口之前 |
| `crm.db` 正常生成、端口也分配了 | 这些步骤在 panic 之前 |
| `cargo build` 完全成功、0 错误 | 这是**运行期** panic，编译器管不着 |

**正确写法**：把 `from_std` 挪进 `async_runtime::spawn` 出来的 async 块里，在块内做转换。

```rust
tauri::async_runtime::spawn(async move {
    match tokio::net::TcpListener::from_std(std_listener) {
        Ok(listener) => {
            if let Err(e) = axum::serve(listener, app_router).await {
                eprintln!("axum 退出: {e}");
            }
        }
        Err(e) => eprintln!("转换监听器失败: {e}"),
    }
});
```

listener 是**已经 bind 好**的，转换之前到达的连接会由操作系统的 backlog 排队，所以界面哪怕抢先发请求也不会丢 —— 不需要额外做「等后端起来」的同步。

> **教训**：编译通过 ≠ 能跑。打包类任务必须**真的把 exe 启动一次**并检查日志最后一行是不是「窗口已创建」。只看 `cargo build` 的 exit code 会漏掉这一类问题。

### 4.6 第二个坑：窗口只能建一次，配置里必须留空

修好 `from_std` 之后，会立刻撞上下一个坑 —— **症状完全相同**（一闪而过、日志停在「API 地址」、窗口不出现），只有 panic 文案不同：

```text
thread 'main' panicked at tauri-2.11.5\src\app.rs:1425:11:
Failed to setup app: error encountered during setup hook:
创建窗口失败: a webview with label `main` already exists
```

原因：`tauri.conf.json` 的 `app.windows` 里声明了一个 `label: "main"` 的窗口，**Tauri 会在调用 setup 回调之前先把配置里的窗口自动建出来**；`main.rs` 的 setup 里又用同一个 `label` 建了一次，于是 setup 钩子报错、整个进程退出。

**正确做法：配置里留空数组，窗口完全由代码创建。**

```json
"app": {
  "windows": [],
  "security": { "csp": null }
}
```

为什么不能让配置来建窗口？因为需要在窗口上挂 `initialization_script`，把运行期分配的 `http://127.0.0.1:<随机端口>/api/v1` 注入成 `window.__BCRM_API_BASE__`。配置声明的窗口挂不了这个脚本，前端就拿不到地址、只能退回 mock 数据。所以职责划分是：**端口分配与地址注入在代码里，窗口参数也必须跟着在代码里**，两者保持在同一处维护。

> **排查手法**：exe 同级的 `bcrm-launcher.log` 是**多个实例共用同一个文件**、且以追加方式打开。如果同时启动过两个实例，后者的启动横幅会把前者的「窗口已创建」挤到中间，容易误判。稳妥的验证方式是同步启动并把 stdout/stderr 抓下来：
>
> ```bash
> node -e "const{spawnSync}=require('child_process');\
> const r=spawnSync('Application/bcrm-desktop.exe',[],{cwd:'Application',encoding:'utf8',timeout:15000});\
> console.log('status',r.status);console.log(r.stderr)"
> ```
>
> `status 101` 就是 Rust panic 退出码，配合 stderr 里的 panic 文案可以一步定位。

### 4.7 第三个坑：WebView2 数据目录被管理员占用 → 「双击打不开」

**现象**（本项目实际踩过）：`bcrm-desktop.exe` 双击**没有任何窗口**（进程起来又退出）；
但**重新运行安装程序时自动打开却能开**；同一个 exe 在**别的电脑双击正常**，只在**某些电脑**不行。

**根因**：Tauri 用 WebView2 渲染界面，其用户数据目录默认在 `%LOCALAPPDATA%\<identifier>`（本项目为 `%LOCALAPPDATA%\com.bcrm.desktop`）。
**一旦该目录是被管理员权限的进程创建的**（安装向导结尾的「自动运行」就是提权身份，或曾手动「以管理员身份运行」过一次），目录及其下全部文件的所有者会变成 `BUILTIN\Administrators`；之后以**普通用户**双击时，WebView2 无法接管这个「管理员所有」的目录，窗口就建不出来。

这恰好解释了三件事：安装向导（提权）自动打开能开 · 之后普通双击打不开 · 别的电脑（一路普通用户）正常。

**判定**（PowerShell）：

```powershell
(Get-Acl "$env:LOCALAPPDATA\com.bcrm.desktop").Owner   # 输出 BUILTIN\Administrators 即为中招
```

**修复**：删掉该目录（是可再生的缓存，**不含任何业务数据**），再以普通用户双击即可重建；或直接双击随附的 `Application/修复启动.bat`（先清理再启动）。

```powershell
[System.IO.Directory]::Delete("$env:LOCALAPPDATA\com.bcrm.desktop", $true)
```

**预防**：始终**直接双击 / 走快捷方式**启动，**不要右键「以管理员身份运行」**。

> 经验教训：这类「编译 0 错误、别的机器能跑、就这台不行」的问题，根因往往在**用户环境状态**（权限 / 缓存 / 残留），而不在代码。先量环境（进程、日志、数据目录属主），再动代码。

## 五、打包常见坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `LNK1104: cannot open file 'bcrm_backend.exe'` | 上一轮的后端进程还占着 exe（Windows 文件锁） | 停掉占用端口的进程再编译。本项目自带 `tools/_dev_restart.mjs` 做「停 → 编译 → 起」 |
| exe 编好了但界面是旧的 | `frontend/dist` 没重建 | 严格按 4.1 的顺序：先后端前端 build，再 cargo build |
| 双击无窗口、进程一闪而过 | ① setup 钩子 panic（见 4.5 / 4.6）② 缺 WebView2 ③ 数据库目录不可写 | 看 exe 同级 `bcrm-launcher.log` 与 `bcrm-launcher-error.log`；仍不明就把 stdout/stderr 抓下来看 panic 文案 |
| **双击打不开，但安装后自动打开能开 / 别的机器能跑就这台不行** | WebView2 数据目录 `%LOCALAPPDATA%\com.bcrm.desktop` 被管理员占用（见 4.7） | 删除该目录，或双击 `Application/修复启动.bat`；以后**不要「以管理员身份运行」** |
| `a webview with label 'main' already exists` | `tauri.conf.json` 的 `app.windows` 与 `main.rs` 重复建了同名窗口 | 配置里改成 `"windows": []`（见 4.6） |
| 编译到 `webview2-com` 失败 | Rust 目标是 `-gnu` 而非 `-msvc` | `rustup default stable-x86_64-pc-windows-msvc` |
| 首次 `cargo build` 很慢（5–15 分钟） | Tauri 依赖树约 500 个 crate + `lto=true` + `codegen-units=1` | 正常现象。后续增量编译只需几十秒 |
| 想减小体积 | release profile 已开 `lto/strip/codegen-units=1` | 已优化；再压需换 `opt-level="z"`，收益有限 |

## 七、从 DDL 重新生成文档与元数据（改表结构时）

**单一事实来源**是 `客户管理系统SQLite建库语句.md`（DDL）。任何表结构改动都要走这条流水线，否则文档与库会漂移：

```bash
python tools/build_api_docs.py
# 产出：
#   backend/resources/schema.json        → 后端编译期内嵌的表白名单
#   客户管理系统表结构元数据.json          → 前端表单/筛选器用的元数据
#   客户管理系统API接口文档.md（附录）     → 逐表字段说明
```

改完必须**重新编译后端**（因为 `schema.json` 是 `include_str!` 编进二进制的），且前端也要重新 build。
