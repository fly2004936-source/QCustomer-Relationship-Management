# 07 · 项目功能介绍

> 这是一套面向**大客户销售**的客户关系管理系统（CRM）：围绕「客户 → 人员 → 项目 → 合作竞争方」的关系网络，把决策链、竞争态势和行动计划放在同一张图上，并提供 62 张业务表的通用数据管理。
>
> 交付形态（均在项目根目录）：`Application/bcrm-desktop.exe`（Tauri 单文件，双击即用）、`Application/BCRM客户管理系统_1.0.0_x64-setup.exe`（NSIS 安装包，已离线捆绑 WebView2）、`EXE/`（前后端分离便携版，`start.bat` 一键启动）。
> 数据库默认与 exe 同目录（便携），目录不可写时回退到 `%LOCALAPPDATA%\Bcrm\crm.db`。

---

## 一、它解决什么问题

大客户销售的核心困难不是「记不住客户」，而是：

| 困难 | 本系统的应对 |
| --- | --- |
| 客户组织里谁拍板、谁支持、谁反对，散落在各人脑子里 | **关系网络图**：把人员按决策角色和态度可视化，一眼看出决策链 |
| 这个项目到底有几成把握？凭什么？ | **C74111 诊断**：7 Clears + 4 Priorities + 1 Key，100 分制，给出态势与承诺判定 |
| 合作方、竞争方各是谁在跟？跟到什么程度？ | **项目作战板**：实体级 + 人员级两层关联，含动向与策略 |
| 拜访完就忘，行动项没人跟 | **拜访行动域**：拜访记录 + 我方人员 + 拜访对象 + 行动项 |
| 数据分散在多张表，业务人员不会写 SQL | **通用数据管理**：62 张表统一界面，每列都能点一下筛选，支持多条件 AND/OR |

## 四、关系网络（核心界面）

这是系统的**主视图**，把抽象的关系变成一张可拖拽的图。

### 4.1 图的构成

节点分几类：

| 节点类型 | 代表 | 说明 |
| --- | --- | --- |
| 客户 | `customer` | 主客户 / 关联客户 |
| 人员 | `person` | 客户方人员 |
| 项目 | `project` | 挂在主客户下 |
| C74111 | `project_c74111` | **独立节点**（不是项目的附属属性，而是可评分的对象） |
| 合作方 | `coop_entity` | `entity_type = partner` |
| 竞争方 | `coop_entity` | `entity_type = competitor` |
| 我方人员 | `internal_person` | 我方派出人员 |

### 4.2 人员节点的视觉编码

人员节点同时表达**两维信息**：

- **ADUR 决策角色**：A（决策）/ D（推动）/ U（使用）/ R（把关）—— 用配色区分
- **态度**：`+` 支持 / `=` 中立 / `-` 反对 / `X` 未知 / `⭐` 关键支持者 —— 用字符标注

这样一眼能看出「谁支持我、谁能拍板、谁在挡」。

### 4.3 交互

| 操作 | 效果 |
| --- | --- |
| 拖拽节点 | 自由布局，方便理清结构 |
| 单击节点 | 打开信息浮层（`DraggablePanel`） |
| 点 C74111 节点 | 打开 **C74111 评分面板**，可直接改分保存 |
| 点项目节点 | 展开 **项目作战板** |
| 「全部展开」 | 一键展开所有节点 |
| 「收起面板」 | 隐藏右侧信息栏，获得更大画布 |

### 4.4 项目作战板（四要素）

点开项目节点后展示四块内容，正好对应实际作战需要回答的四个问题：

**① 相关人员** —— 客户方决策链
- 按 ADUR 角色分组（决策 / 推动 / 使用 / 把关）
- 每人显示态度与岗位
- 点人员可查看详情

**② C74111 分档** —— 这个项目几成把握
- 总分 + 分档（绝对优势 / 相对优势 / 相对劣势 / 绝对劣势 / **未诊断**）
- 趋赢力百分比
- 竞争策略文本

**③ 奇安信派出人员** —— 我方谁在跟
- 内部人员列表（含职级、部门、组织）

**④ 合作方 / 竞争方参与情况** —— 场上有谁
- 每方列出：参与人员、最近动向、竞争策略与动作
- 这是**两层关联**的体现：公司层面的参与（`*_project_rel`）+ 具体对接人（人员级 rel）

### 4.5 C74111 评分面板

点开后可**直接改分并保存**：

| 板块 | 项数 | 满分 |
| --- | --- | --- |
| 7 Clears | C1 客户组织结构图(10) + C2 拍板人燃眉之急(5) + C3 立项六要素(5) + C4 采购周期(5) + C5 合作方三问(5) + C6 竞争方三问(5) + C7 独特客户价值(5) | **40** |
| 4 Priorities | P1 项目组多数人支持(5) + P2 合作伙伴代理商支持(5) + P3 与拍板人密谋策划(20) + P4 关键人密谋策划(10) | **40** |
| 1 Key | 与最高决策人密谋策划 | **20** |
| | | **100** |

- `P3` / `P4` / `Key` 右侧有 **☆ 按钮**：打满即标记（落库为 `p3_star` / `p4_star` / `key_star` = 1）
- 总分自动重算 = 7C + 4P + Key
- 趋赢力 = 总分 / 100 × 100%
- 手动可填「可否承诺」与「竞争态势」（两个枚举）
- 保存走 `POST /project_c74111/upsert`（`project_id` 唯一，天然幂等）

**分档与承诺口径**：

| 总分 | 态势 | 承诺 |
| --- | --- | --- |
| > 75 | 绝对优势 | **可承诺** |
| 50 – 75 | 相对优势 | **可争取** |
| 25 – 50 | 相对劣势 | **可参与** |
| < 25 | 绝对劣势 | **不可承诺** |
| 无记录 | 未诊断 | 待评分 |

面板带四角标记与网格底纹、数字走等宽字体 —— 「控制台」视觉。所有颜色 / 圆角 / 阴影 / 动效都读 `themes.css` 的语义令牌，所以 **11 套风格、明暗两种基调会把驾驶舱整体重绘**。

- 客户方人员态度取 `project_member.attitude`（**`person` 表没有 `attitude` 列**）；合作 / 竞争 / 我方三张人员表自带 `attitude`。

## 六、数据管理（62 张表的统一界面）

从左侧栏点任意表进入。这是「前端能不能对**所有表、所有字段**做增删改查」的直接体现。

### 6.1 界面构成

```text
┌─ 页头 ─────────────────────────────────────────────────┐
│ 客户主档  customer   [标签]           [新建行] [刷新]   │
├─ 工具条 ───────────────────────────────────────────────┤
│ [关键字搜索…] [搜索] [清除]        [☑ 紧凑列宽]        │
├─ 条件筛选 ─────────────────────────────────────────────┤
│ [条件筛选 ▾]  [全列等值（取第 1 行）]                  │
│ ┌ 列 ▾ │ 操作符 ▾ │ 值 ──────── │ 逻辑: 全部▾ │ ✕ ┐  │
│ └ ...多行，可增删...                                ┘  │
│ [添加条件] [应用筛选] [清空全部]                       │
│ GET /customer?filter[industry]=能源&filter[level]=…    │
├─ 表格 ─────────────────────────────────────────────────┤
│ id* │ crm_code 🔽 │ name 🔽 │ category 🔽 │ … │ 操作   │
│  3  │ S003       │ 丙能源 │ 关联客户   │ … │ ✎ 🗑   │
├─ 分页 ─────────────────────────────────────────────────┤
│           共 11 条 · 第 1/6 页   [上一页] [下一页]      │
└────────────────────────────────────────────────────────┘
```

### 6.2 三种查询方式

| 方式 | 怎么做 | 对应需求 |
| --- | --- | --- |
| **关键字** | 输入框，对全表文本列模糊匹配 | 快速找东西 |
| **单字段筛选** | **点表头的漏斗图标** → 自动为该列生成条件（默认取第 1 行的值） | 「所有字段**单独**查询」 |
| **多字段联合** | 「添加条件」逐行加，切「全部满足（AND）/ 任一满足（OR）」 | 「所有字段**联合**查询」 |

### 6.3 全列等值：一键验证全字段可查

点「全列等值（取第 1 行）」，系统会用当前**数据最全的那一行**，为这张表**每一列**各生成一条等值条件：

- 普通列 → `等于`
- 枚举列 → 下拉取值
- 布尔列 → `0` / `1`
- JSON 列 → 自动换成 `json_contains`（传裸元素）

然后点「应用筛选」。**结果必然命中那一行**——如果某列筛完是 0 条，说明该列查询链路有问题。

这让「证明这张表每个字段都能查」从人工点几十次变成**一次点击**。

### 6.4 操作符按列类型收窄

筛选器的操作符下拉**只列出该列类型支持的**：

| 列类型 | 可用操作符 |
| --- | --- |
| 文本 | 等于 / 不等于 / 包含 / 不包含 / 以…开头 / 以…结尾 / 在列表中 / 不在列表中 / 为空 / 不为空 |
| 数值 | 等于 / 不等于 / 大于 / 大于等于 / 小于 / 小于等于 / 区间 / 在列表中 / 不在列表中 / 为空 / 不为空 |
| 枚举 | 等于 / 不等于 / 在列表中 / 不在列表中 / 为空 / 不为空 |
| 布尔 | 等于 / 不等于 / 为空 / 不为空 |
| JSON | JSON 含元素 / JSON 含全部 / JSON 完全等于 / JSON 文本包含 / JSON 长度≥ / 为空 / 不为空 |

枚举列的值控件是**下拉**（选项来自元数据），所以**不可能填出非法的枚举值**。

### 6.5 请求串预览

筛选面板底部实时显示即将发出的查询串：

```
GET /customer?filter[industry]=能源&filter[level__in]=P1,P2&page=1&page_size=20
```

**作用**：让业务人员看懂界面在做什么；同时让**验证脚本可以把这串原样重放一次**，证明界面拼出来的语法确实是后端能接受的那种。

### 6.6 增删改查

| 操作 | 说明 |
| --- | --- |
| **新建** | 弹窗表单；控件按列类型自动生成（枚举→下拉、外键→下拉、布尔→开关、JSON→文本域）；必填由元数据推出 |
| **编辑** | 点行尾 ✎；只提交改动的字段（`PATCH`） |
| **删除** | 点行尾 🗑；二次确认后按主键删除 |
| **外键友好显示** | 外键列在表格里显示成**名称**（如客户名），不是 id |
| **紧凑列宽** | `project` 表 43 列，默认只显示主键 + 前 11 个非 JSON 列，避免横向铺满 |
| **分页** | 与服务端 `total` / `page_count` 对齐 |

## 八、数据源：演示数据 / 实时数据

界面右上角可切换：

| 模式 | 数据来源 | 用途 |
| --- | --- | --- |
| **演示数据** | 内置静态数据 | 不用连数据库就能看完整界面；后端不可用时的兜底 |
| **实时数据** | 后端 10 张核心表（客户/项目/人员/成员/合作方/合作方人员/竞争方人员/我方人员/组织/C74111） | 真实业务 |

**切换失败不会白屏**：实时模式连不上后端时，会自动回落到演示数据并显示错误原因。同时界面会显示后端实际数据库路径与各表行数——这样能一眼区分「接上了但表是空的」和「根本没接上」。

### 空库首启会自动补一批工作台内容

工作台的 11 个功能里有 4 个（资讯 / 客户更新 / 竞品动态 / 快捷入口）得有数据才看得出效果。所以 `api/seed.js` 的 `ensureWorkbenchSeed()` 会在**对应表为空时**补一次：

| 表 | 补什么 | 前置条件 |
| --- | --- | --- |
| `news_item` | 14 条行业议题（网络安全 / AI / 金融科技三类） | 无 |
| `dashboard_shortcut` | 6 个真实可访问的站点（不留死链） | 无 |
| `dashboard_update_log` | 1 条「系统初始化」批次记录 | 无 |
| `customer_news` | 每个客户 2 条信息更新素材 | 需要库里有 `customer` 行 |
| `entity_history` / `entsales_confrontation` | 每个竞争方 2 条动向 / 若干对抗记录 | 需要库里有 `coop_entity` 行 |

三条设计约束：**已有数据就完全不动**（只补空表）；客户/竞品相关的记录会去读真实的 `customer.id` / `coop_entity.id`，**保证外键指向存在的行、不产生脏数据**；资讯的 `source` 一律写成「演示数据」，界面上能一眼看出不是真实抓取。任何一步失败都不抛错 —— 工作台照常可用，只是对应卡片显示为空。

## 十、这个系统已验证到什么程度

| 验证 | 规模 | 结果 | 报告 |
| --- | --- | --- | --- |
| **后端接口层**（真实 HTTP） | **8399 条断言**：62 张表 × 建行/读回/每列单独查询/多字段联合查询/count/exists/by/export/排序/子表/批量增改删/按主键删/按条件删 | ✅ **全部通过，0 失败 0 跳过** | `.workbuddy/verify/report.json` |
| **前端界面层**（真实浏览器 + 真实点击） | 62 张表：侧边栏进入 → 条件筛选（含 **逐列驱动界面筛选**）→ 新建 → 编辑 → 删除 → 重放界面请求串比对 | ✅ 见 `.workbuddy/verify/ui-report.json` | 同上 |

界面层验证脚本 `tools/_verify_crud_ui.mjs` 的特点：

- **不直接调 API**，全部走界面点击，测的是「用户真的能做到吗」
- **逐列驱动界面筛选**：每一列都真的改一次筛选控件、点一次「应用筛选」、读回结果行数 —— 这是「每个字段单独查询」的界面级证据
- **重放界面请求串**：把界面显示的查询串原样再发一次，比对行数一致，证明请求串不是装饰
- 会自动**按拓扑序补空父表**（否则从表在界面上建不出行，会产生假失败）

本轮修复的真问题：

| # | 层 | 问题 | 性质 |
| --- | --- | --- | --- |
| 1 | 后端 | `or[0][列名]` / `and[0][列名]` 分组查询一律报「列不存在」 | **真 bug**（参数解析），已修 |
| 2 | 后端 | `json_len_gte` 恒查不到数据（SQLite 类型排序 + 错误绑定类型） | **真 bug**，已修 |
| 3 | 前端 | 外键信息读错了位置（列级 `references` 全为 null，实际在表级 `foreignKeys`）→ 外键下拉/标签**从未生效** | **真 bug**，已修 |
| 4 | 打包 | 桌面壳在 `.setup()` 里直接调 `TcpListener::from_std`，触发 `there is no reactor running` panic → **exe 一闪而过、窗口永远建不出来**（`cargo build` 却是 0 错误） | **真 bug**，已修（改为在 async 块内转换） |
| 5 | — | 缺少条件筛选器（原版只有一个关键字框） | **功能缺口**，已补 |
| 6 | 打包 | `tauri.conf.json` 已声明 `label:"main"` 的窗口（Tauri 会自动建），`main.rs` 又建了一个同名的 → `创建窗口失败: a webview with label 'main' already exists` → **症状与第 4 条完全一样**：一闪而过、日志停在「API 地址」 | **真 bug**，已修（配置改成 `"windows": []`，窗口完全交给代码创建） |
| 7 | 验证脚手架 | 多态表 `person_form` / `person_disc` 的唯一键是 `person_type + person_id`，但这两列**没有数据库外键约束**（id 指向哪张表取决于 type，DDL 写不出来）→ 被「唯一键每列都是外键」的筛选漏掉 → 不重试、永远撞 UNIQUE，报告里表现为一条**假失败** | 脚手架缺口，已修（先查库里已占用的组合，再挑一个空闲组合） |
| 8 | 前端 | 界面右下角常驻 **5 个灰色小横条**（190×20px、无文字、永不消失）。轻提示容器写成 `v-for="t in toasts.items"`，而 `items` 是挂在**普通对象**上的 ref —— 模板只解包 setup 顶层绑定，不解包嵌套 ref，于是 `v-for` 遍历了 `RefImpl` 的 5 个可枚举内部属性（`_value`/`_rawValue`/`dep`/`__v_isRef`/`__v_isShallow`） | **真 bug**，已修（把 ref 提成顶层绑定；实测修复后加载为 0 条、触发 1 条正常提示、4.2 秒后自动消失） |

> 第 4、6 两条特别值得一提：它们**只有把 exe 真启动一次**才会暴露。编译通过、产物存在、数据库都能正常生成，但程序在建窗口前就 panic 了。而且这两个坑是**串联**的 —— 第 4 条 panic 时根本走不到建窗口那一步，修好它才会露出第 6 条。纯靠「构建成功」的日志永远发现不了这类问题。
>
> 第 7 条是另一类教训：**验证脚本自身的缺口会伪装成产品缺陷**。如果不追根因，很容易得出「`person_form` 不支持新增」的错误结论。判定方法很简单 —— 用后端接口直接建一行：能建，就是脚手架的问题。

## 十一、快速上手

### 作为使用者

1. 双击 `Application/bcrm-desktop.exe`（或先跑 `Application/BCRM客户管理系统_1.0.0_x64-setup.exe` 安装）
2. 默认进入工作台；顶部导航切换到「数据分析」看驾驶舱，左侧栏点任意表进入数据管理
3. 在数据管理页：
   - 想按某列筛选 → **点表头漏斗**
   - 想多条件组合 → **添加条件** + 切 AND/OR + **应用筛选**
   - 想验证全字段可查 → **全列等值（取第 1 行）** + 应用筛选
   - 想新增/编辑/删除 → 右上「新建行」/ 行尾 ✎ 🗑

### 作为开发者

见 `01-环境准备与打包指南.md`。常见动作：

```bash
cd backend   && cargo run -- --port 8787 --db ../data/crm.db   # 起后端
cd frontend && npm run dev                                    # 起前端（5173）

# 打包：先出前端产物，再编桌面壳（顺序不能反）
cd frontend && npm run build
cd ../launcher && cargo build --release          # → launcher/target/release/bcrm-desktop.exe
cd ../launcher && cargo tauri build              # → .../bundle/nsis/*.exe（NSIS 安装包，含 WebView2）
```
