# 06 · 数据库架构解析

> **62 张表 / 848 列 / 55 条外键（分布在 40 张表） / 32 个索引 / 10 组唯一键 / 44 组枚举**。
> 另有 9 个 JSON 列、11 个布尔列、149 个 NOT NULL 列。
>
> 本文讲这套 schema 怎么切、为什么这么切、以及容易踩的口径问题。
> 建库语句的完整 DDL 见 `客户管理系统SQLite建库语句.md`（**唯一事实来源**），逐表字段说明见 `客户管理系统数据库说明表（SQLite）.md`。

## 一、技术约定

| 项 | 约定 |
| --- | --- |
| 主键 | `id INTEGER PRIMARY KEY AUTOINCREMENT` |
| 金额 | `REAL`，**单位：万元** |
| 日期 / 时间 | `TEXT`，ISO8601（`YYYY-MM-DD` / `YYYY-MM-DD HH:MM:SS`） |
| 布尔 | `INTEGER` 0/1 |
| 枚举 | `TEXT` + `CHECK` 约束 |
| 多值 / 嵌套 | `TEXT` 存 JSON 文本，走 SQLite JSON1 函数查询 |
| 外键 | `PRAGMA foreign_keys=ON`（每连接设置），`ON DELETE` 按语义选 `CASCADE` / `SET NULL` |
| 日志模式 | WAL |
| 外键列命名 | 单数表名 + `_id`，如 `customer_id`、`project_id` |

> ⚠️ **WAL 的运维含义**：库文件旁边会有 `crm.db-wal` / `crm.db-shm`。**复制数据库要三个一起复制并同名**，否则可能丢失最近未 checkpoint 的事务。正常关闭应用时 SQLite 会自动 checkpoint。

## 三个关键设计决策

## 三、决策一：产品/实体合并，人员分表

### 现象

- **产品/竞争方**：`coop_entity` **一张表**，用 `entity_type ∈ {partner, competitor, both}` 区分
- **人员**：**四张表** —— `person` / `partner_person` / `competitor_person` / `internal_person`

看起来不对称，是刻意的。

### 为什么实体合并

合作方和竞争方的**属性高度重合**（公司类型、代理层级、独家承诺、关系性质、区域…），差异只在归属。如果拆成两张表：

- 「既是合作方又是竞争方」的实体（`both`）无处安放，只能建两行，导致同一个公司在两处维护
- 12 张 `entsales_*` 销售分析表要写两套外键

合并成 `coop_entity` 后，`entsales_*` 和 `entity_history` 统一用 `entity_type + entity_id` 指向它。

### 为什么人员必须分表

人员**差异是实质性的**，不是标签差异：

| | `person` | `partner_person` | `competitor_person` | `internal_person` |
| --- | --- | --- | --- | --- |
| 挂靠 | `customer_id` | `coop_entity_id` | `coop_entity_id` | `org_id` |
| 独有字段 | 客户方 ADUR 角色、决策角色 | 合作方立场、影响力 | 竞争方情报能力、对抗记录 | 内部职级、汇报线 |
| 列数 | 28 | 32 | 32 | 29 |

硬合一张表会得到一张「一半列对一半行是 NULL」的表，且丢掉外键约束（`customer_id` 和 `org_id` 不能同时 NOT NULL 且互斥）。**分表后每张表的外键都是干净的。**

### 代价

「查某人是谁」需要先知道类型，再决定查哪张表。所以 6 张**画像表**用多态（见下一节）横跨四种类型：`person_type + person_id`。

---

## 四、决策二：多态表承载跨类型共性

**21 张表**用多态外键：

| 多态键 | 表 | 指向上游 |
| --- | --- | --- |
| `person_type` + `person_id` | `person_form`、`person_disc`、`person_burning_issue`、`person_attitude_log`、`person_assessment`、`person_intel` | `person_type ∈ {customer, partner, competitor, internal}` → 分别指向四张人员表 |
| `entity_type` + `entity_id` | `coop_entity`、`entity_history`、`entsales_*`（12 张） | → `coop_entity` |

### 为什么用多态而不是四张分表

画像类数据（FORM 测评、DISC、态度日志、燃眉之急…）的**结构对四种人员完全一样**。如果按类型拆表，6 张画像 × 4 种类型 = 24 张表，而且「给所有类型的人查一次态度变化」要写 UNION。

多态表让「横跨类型」的查询变成一条 SQL。

### 代价：没有数据库级外键约束

`person_id` 是 `INTEGER`，但**不能声明 FOREIGN KEY** —— 因为目标表取决于 `person_type`。所以：

- **完整性由应用层保证**：写入时先校验「`person_type` 对应的那张表里确实有 `person_id`」
- 删除人员时**不会级联**，需要应用层清理画像数据

> 这也是验证脚本踩过的坑：`person_form` / `person_disc` 的唯一键是 `person_type + person_id`，但没有外键约束，所以「换父 id 绕开唯一键冲突」这招不生效——必须真的换一个 `person_type`/`person_id` 组合。

## 五、决策三：项目只挂主客户

```sql
-- project.customer_id → customer.id
```

**硬规则（应用层保证）**：`project.customer_id` 指向的客户，其 `category` 必须是 `主客户`。

### `customer.category` 的语义（重要口径）

| 值 | 含义 | 能挂什么 |
| --- | --- | --- |
| **主客户** | 我方**直接经营**、背业绩指标的对象 | ✅ 项目、人员、拜访、预算、业绩 |
| **关联客户** | 只出现在关系网里、不由我方直接经营的单位 | ❌ **不能挂项目**；只通过 `customer_relation` 参与关系网 |

**关联客户包括**：上级集团、下属分公司、兄弟单位，甚至**奇安信集团自身**也被登记为关联客户。

两者之间用 `customer_relation` 记录：

```sql
customer_relation(
  customer_id,           -- 主客户
  related_customer_id,   -- 关联客户（**可为空**）
  relation_type,         -- 上级 / 下属 / 合作 / 平级
  main_purchase          -- 是否主体采购
)
```

`related_customer_id` 可空是刻意的：**允许只登记一个名称而不在 `customer` 建档**。现实里关系网中存在大量「知道有这么个单位，但不必作为客户管理」的对象。

> 唯一的硬限制就是项目：`project.customer_id` 不接受 `category='关联客户'` 的记录。这条由应用层校验，DDL 层做不到（需要跨表 CHECK）。

## 六、关联关系全景

### 6.1 客户侧

```text
customer ──1:1── customer_profile
   │
   ├──1:N── customer_{relation, exec_meeting, budget, sales_data, tender,
   │                    purchase, foreign_product, need, opportunity,
   │                    competition, target, perf_dashboard, action_plan}
   ├──1:N── customer_budget ──1:N── customer_budget_detail
   ├──1:N── customer_team
   ├──1:N── customer_news
   └──M:N── customer（自反，经 customer_relation）
```

### 6.2 人员侧

```text
customer ──1:N── person
coop_entity ──1:N── partner_person
coop_entity ──1:N── competitor_person
org ──1:N── internal_person
org ──自反── org（parent_id 组织树）

四类人员 ──多态── person_{form, disc, burning_issue, attitude_log,
                            assessment, intel}
```

### 6.3 项目侧（注意合作竞争方是**两层**）

```text
customer ──1:N── project          （只挂主客户）
project ──1:1── project_c74111    （project_id UNIQUE）
project ──1:N── project_action_plan
project ──M:N── person            （project_member，ADUR/态度随项目）

合作竞争方与项目的关系是**两层**：
  实体级：coop_entity ──M:N── project   （经 coop_entity_project_rel）
  人员级：partner_person    ──M:N── project  （经 partner_person_project_rel）
          competitor_person ──M:N── project  （经 competitor_person_project_rel）
```

**为什么要两层**：一个合作方公司可能整体参与项目，但实际落地的只有其中某几个商务。只记实体级会丢掉「谁在跟」；只记人员级会丢掉「公司层面的合作协议」。所以两层并存。

### 6.4 销售分析侧

```text
coop_entity ──多态── entsales_{perf, product, market, distribution, channel,
                               pricing, customer_share, tender, confrontation,
                               tactic, benchmark, plan, source}
coop_entity ──多态── entity_history（实体动向）
```

### 6.5 拜访侧

```text
visit_record（我方人员 via internal_person）
   ├──1:N── visit_our_staff     （visit_id + internal_person_id 唯一）
   ├──1:N── visit_object        （拜访了对方谁）
   └──1:N── visit_action_item   （产生的行动项）
```

> **注意**：`visit_record` 里我方人员指向 `internal_person`，**不是 `person`**。因为拜访是「我出去」，主体必然是我方人员。这一点在写查询时最容易搞错。

### 6.6 外键被引用热度

| 被引用表 | 引用次数 |
| --- | --- |
| `customer` | **23** |
| `project` | **14** |
| `coop_entity` | 3 |
| `person` | 3 |
| `visit_record` | 3 |
| 其它 | 其余 |

**实践含义**：`customer` 和 `project` 是最关键的两个父表，任何批量导入都要先建它们。

## 七、唯一键（10 组）

| 表 | 唯一键 | 语义 |
| --- | --- | --- |
| `customer` | `crm_code` | 客户编号 |
| `customer_profile` | `customer_id` | 一客户一画像（1:1） |
| `project_c74111` | `project_id` | 一项目一诊断（1:1） |
| `person_form` | `person_type + person_id` | 一人一 FORM |
| `person_disc` | `person_type + person_id` | 一人一 DISC |

| 字段 | 说明 |
| --- | --- |

| `win_rate` | 趋赢力 = `total_score / 100 × 100%` |
| `competition` | 竞争态势（枚举，4 档） |
| `commitment` | 可否承诺（枚举，4 档） |
| `strategy` / `action_plan` | 竞争策略与行动计划 |
| `updated_at` | 默认 `datetime('now','localtime')` |

### 分档判定

| 总分 | 态势 | 承诺 |
| --- | --- | --- |
| **> 75** | 绝对优势 | 可承诺 |
| **50 – 75** | 相对优势 | 可争取 |
| **25 – 50** | 相对劣势 | 可参与 |
| **< 25** | 绝对劣势 | 不可承诺 |
| 无记录 | **未诊断** | 待评分 |

> **必须单列「未诊断」档**：不加这一档，没有诊断记录的项目会被当成 0 分，界面显示「0 分 · 绝对劣势 · 不可承诺」——这是误导性的，**没评过和评完得 0 分是两件事**。
>
> 边界归属：**75 分归「相对优势」**（`>75` 才是绝对优势）。

## 十、DDL 是唯一事实来源

```text
客户管理系统SQLite建库语句.md      ← 唯一事实来源（DDL）
        │
        │  python tools/build_api_docs.py
        ▼
backend/resources/schema.json          → 后端编译期内嵌（include_str!）→ 表白名单
客户管理系统表结构元数据.json            → 前端表单/筛选器/导航树
客户管理系统API接口文档.md（附录）       → 逐表字段说明
```

**改表结构的正确流程**：

1. 改 `客户管理系统SQLite建库语句.md`
2. 跑 `python tools/build_api_docs.py`
3. 重新编译后端（`schema.json` 是 `include_str!`，必须重编）
4. 重新构建前端

**跳过第 2–3 步的后果**：后端白名单还是旧的，新列查不到、新表 40004；前端表单缺列。这类问题表现为「数据库里明明有这列，接口却说列不存在」，排查起来很绕——所以**务必走完整流程**。

## 十一、空表与外键依赖（做数据准备时看这张）

**22 张表没有外键约束**（可自由写入）：`customer`、`coop_entity`、`org`、`news_item`、`dashboard_*`、全部 13 张 `entsales_*` 等。

**40 张表带外键**，其中受影响最大的：

| 父表 | 被多少张表依赖 | 说明 |
| --- | --- | --- |
| `customer` | 23 | 不先建客户，绝大多数表都写不进去 |
| `project` | 14 | 不先建项目，`project_member` / `c74111` / 三张 `*_project_rel` 都空 |
| `visit_record` | 3 | 空的话三张 `visit_*` 从表在界面上**建不出行**（必填外键没有可选项） |
| `coop_entity` | 3 | — |
| `person` | 3 | — |

> **实战提示**：验证或演示前，先按 **`customer` → `project` → `visit_record` → 从表** 的顺序播种。本项目 `tools/_verify_crud_ui.mjs` 里内置了这一步（自动按拓扑序补空父表），否则会出现「这几张表不支持新增」的假结论。
