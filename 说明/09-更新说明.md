# 09 · 更新说明（桌面版 v1.0.0 交付修订）

> **本轮主题**：让「普通用户双击就一定能打开」，并把它做成可重复、可自检、可交付的一条流水线。
>
> **适用对象**：交付负责人 / 现场支持（IT）/ 后续维护者。使用者请直接看交付目录里的 `使用说明.txt`。
>
> **文档口径**：本轮**没有 git**，无法按提交记录出变更日志，所以本文按「改了哪些文件 + 行为变化 + 实测证据」组织。
> 改动时间集中在 **2026-09-15 22:30 – 2026-09-16 00:07**。

---

## 一、一句话摘要

上一版把系统跑通了，但**交付到别人机器上会开不了窗口**。本轮把三类「双击没反应」的根因逐个处理掉：
数据库权限、WebView2 运行时、WebView2 缓存目录被提权占用；同时补上**自检入口**、**一键修复脚本**与**一条命令的构建流水线**。
最后发现还有第四类根因（企业终端安全软件用**云端规则**拦截「陌生软件」，**与签名无关**），**程序无法规避**，已在交付文档里给出三种应对方案。

## 二、改了什么

### 2.1 数据库位置与权限：从「一次判定」改成「候选位逐个实测」

**问题**：旧版只判断一次「exe 同级能不能写」，不能写就直接失败。装到 `C:\Program Files` 后普通用户双击 → 建库失败 → 进程在出窗口前退出 → 用户看到的是「双击没反应」。
更隐蔽的是**已有数据的情况**：如果管理员装机器时导入过数据，普通用户回退到空库、会以为数据丢了。

**改法**（`backend/src/db.rs`）：

| 机制 | 说明 |
| --- | --- |
| 三级候选位 | ① exe 同级 `crm.db`（便携，首选）→ ② `%LOCALAPPDATA%\Bcrm\crm.db`（用户目录）→ ③ 当前工作目录 `./crm.db`（兜底）。同路径自动去重 |
| 逐个实测 | 每个候选位连过三关才算可用：**目录可写** → **已有库可写** → **写探针**；任何一关失败就记下原因、换下一个 |
| 写探针 | `BEGIN IMMEDIATE` + 建表 + 删表 + **ROLLBACK**，不留残留对象。只读库 / 只读目录会在这一步就暴露 |
| 初始数据搬运 | 回退到用户目录且目标库不存在时，把候选位里**已有的** `crm.db` **连同 `crm.db-wal`** 拷过去当初始数据（`-shm` 是临时索引，故意不拷） |
| 只搬运「用户数据位」 | 兜底的工作目录不搬，否则会在用户当前目录里凭空多出一个 `crm.db` |
| 失败不爆炸 | `AppState::open_default()` 返回 `DbLocation`（含每个被跳过候选位的原因），启动日志逐条打印；全失败才报错，并把所有原因拼在错误信息里 |

**顺手修掉一个真 bug**：Windows 的 `fs::copy` 会把源文件的**属性一起复制**。源库是只读的（从只读介质/只读共享拷来）时，副本也是只读的 —— 「回退到用户目录」就白做了，照样报 `attempt to write a readonly database`。
这个坑很隐蔽：目录可写、库文件看着也在，只有真去写才炸。现在 `seed_copy()` 之后统一清一次只读属性。

### 2.2 新增数据库自检入口（现场排障用）

新增 `bcrm_backend::diagnostics_report()`，**桌面版与控制台版共用同一份逻辑**，不会漂移。

```bat
bcrm-desktop.exe --db-check            :: 报告写到 exe 同级 bcrm-db-check.txt，并弹窗
bcrm-desktop.exe --db-check --quiet    :: 不弹窗（也可设 BCRM_NO_DIALOG=1），看退出码：0=可用 1=不可用
bcrm-server  --db-check                :: 控制台版，同一份报告
```

报告内容：用户与权限、exe 路径、**每个候选位的「目录是否可写 / 库是否存在 / 库是否可写」**、最终选用位置、表数量、数据行数、写探针结果。
报告文件先写 exe 同级，写不进去再退临时目录 —— 保证线索不会因为权限问题丢掉。

### 2.3 WebView2：装得上、建得出、坏了能自愈

分三件事处理，都在**建窗口之前**完成：

**① 运行时检测（可控地失败）** —— `ensure_webview2()` 用 `tauri::webview_version()` 在建窗口前查询。
缺失时给中文弹窗 + 一键打开微软官方在线引导器（约 2 MB），并附离线内网方案网址。
**不再出现「一闪而过、什么都没留下」**。

**② 安装包改为内嵌在线引导器** —— `launcher/tauri.conf.json`：

```json
"webviewInstallMode": { "type": "embedBootstrapper", "silent": true }
```

| | 旧（离线安装器） | 新（在线引导器） |
| --- | --- | --- |
| 安装包体积 | 约 208 MB | **约 4.7 MB** |
| 目标机无 WebView2 时 | 完全离线可装 | **安装过程需联网**下载（约 2 MB） |
| 适用场景 | 完全离线内网 | 常规交付 / 联网环境 |

> 若确有「完全离线内网」需求，把 `type` 换成 `offlineInstaller` 重新打包即可，代价是安装包回到约 200 MB。

**③ WebView2 用户数据目录：不再靠 identifier 猜，且能自愈** —— `launcher/src/main.rs`

旧版数据目录固定在 `%LOCALAPPDATA%\com.bcrm.desktop`。**一旦这个目录被提权（管理员）进程创建过**，之后普通用户双击时 WebView2 无法接管它：进程起来了、日志一路正常，**但窗口永远不出现**，而且会一直复现。

现在改成三级候选位（显式通过 `WebviewWindowBuilder::data_directory()` 交给窗口，路径可预期）：

| 优先级 | 位置 | 语义 |
| --- | --- | --- |
| ① | `exe 同级\.bcrm-webview\` | 便携：整目录拷走仍能用，不碰用户系统目录 |
| ② | `%LOCALAPPDATA%\Bcrm\WebView2\` | 与 `crm.db` 同一个 `Bcrm` 目录，便于一起备份/清理 |
| ③ | `%LOCALAPPDATA%\com.bcrm.desktop\` | Tauri 默认位，仅作兜底 |

启动时会**体检目录所有者**：若「目录属于 `Administrators`/`System`，而当前进程不是提权身份」→ 直接删除重建（该目录只是浏览器缓存，**与 `crm.db` 无关**），日志里写明「已自动修复（原属 …）」。
判断「我是不是提权在跑」不引额外依赖：在临时目录建一个探针文件读它的 Owner 当身份参照。

万一窗口仍建不出来，会弹出完整诊断（所有者 / 可写性 / 修法），点「是」即删除并自动重启。

> 编译期踩的一个坑记一下：`tauri::Error` 不是字符串，**不能** `e.starts_with("创建窗口失败")`。
> 要从 `tauri::Error::Setup(s)` 分支取回内层消息再判断。

### 2.4 构建与交付：从手工多步到「一条命令 + 权威源」

**新增 `tools/build_desktop.py`** —— 六步流水线，顺序不可换：

| 步骤 | 做什么 | 为什么在这个位置 |
| --- | --- | --- |
| ① | 校验/生成编译期内嵌资源（`backend/resources/schema.sql`、`schema.json`） | 缺了后端直接以 `os error 3` 编译失败，难一眼看出 |
| ② | 前端构建 `vite build` → `frontend/dist/` | dist 是被编进 exe 的，必须先于 ③ |
| ③ | `cargo build --release` → 便携单文件 exe | 先手动编一次让 ④ 命中缓存，也便于单独交付便携版 |
| ④ | `cargo tauri build` → NSIS 安装包 | 必须在 `launcher/` 目录下执行，**不能带 `--manifest-path`** |
| ⑤ | 汇总交付物到 `Application/` | 源与目标同路径时先判等，避免 `shutil.copy2` 报 WinError 32 |
| ⑥ | 统一编码：`修复启动.bat`→GBK(cp936)、`使用说明.txt`→UTF-8 BOM | 中文 bat 以 UTF-8 落盘会让 `cmd.exe` 按 GBK 解出乱码，连标签跳转都可能失败 |

参数：`--no-frontend`（前端没改）、`--no-installer`（只要便携 exe）、`--collect-only`（不编译，只重新汇总交付目录）。

**新增 `tools/normalize_delivery_files.py`** —— 上表第 ⑥ 步的独立实现，可单独跑。
**新增 `tools/build_schema_resources.py`** —— 从 `说明/08-…SQLite建库语句.md` + `说明/客户管理系统表结构元数据.json` 生成内嵌资源，并**交叉校验**（表名/列名双向比对、重复检测、计数一致性）。支持 `--check` 只校验不写。
**交付辅助文件权威源移到 `tools/delivery/`** —— `Application/` 是纯产物目录，随时可能被清空重建；辅助文件放在里面等于孤本（本仓库已经因此丢过一次，两个文件连同目录一起消失）。

**`修复启动.bat` 重写为五步**（原来是四步）：

| 步骤 | 做了什么 |
| --- | --- |
| 1/5 | **先判断程序能否被系统创建出来**：删旧报告 → 静默自检 → 看报告有没有重新生成。没有就是被终端安全软件拦了，并**自动去搜奇安信天擎的拦截日志** |
| 2/5 | 查 WebView2 运行时（读注册表三个位置），缺了就打开官方安装页 |
| 3/5 | 查三个 WebView2 数据目录的所有者 + 可写性，可疑时问用户要不要删除重建 |
| 4/5 | 展示数据库自检报告摘要（第 1 步已生成好） |
| 5/5 | 启动程序，并提示要收集哪几个文件 |

## 四、已知限制：终端安全软件拦截（程序无法规避）

这是本轮**新查明**的第四类「双击没反应」，也是唯一一类程序自身处理不了的。

| 项 | 内容 |
| --- | --- |
| 现象 | 双击完全没反应、**目录里连 `bcrm-launcher.log` 都没有** |
| 原因 | 企业统一部署的终端安全软件（奇安信天擎 / 深信服 EDR / CrowdStrike 等）用**云端规则**把程序判为「陌生软件」，在内核的**进程创建回调**里就拒绝创建 |
| 本机实测 | 奇安信天擎 10.8.0.8000，判定名 `CloudRule.Block.Strangesoftware`，动作 `建议阻止(2)`、级别 `40`、**静默无弹窗**（`nActionResult=没有这个项(0)`） |
| 日志目录 | `C:\ProgramData\QI-ANXIN Tianqing\Log\module.HipsEngShim\`（判定过程另见 `Log\QCMProcMgr\`） |
| 判别依据 | 程序启动的第一件事就是写日志。**日志一个字都没有 = 进程没被创建 = 不是程序的问题** |

**应对（按推荐顺序）**：

1. **加信任 / 白名单**（推荐）：**优先加「目录」而不是单个文件** —— 本项目每次重新编译 MD5 都会变，按目录加白才能免去反复报备。公司统一管控的机器需要 IT 在管理控制台下发策略。
2. **改交付形态**：本系统是「HTTP API + 浏览器前端」，改成服务端部署 + 浏览器访问，客户端**不创建任何进程**，彻底规避（需先加 API 鉴权）。
3. **给程序签名**：注意——**签名本身不能让它不被拦**，它的价值是让 IT 能按「数字签名名称」加白，从而一次覆盖所有未来版本。

> ⚠️ **三处口径订正**（详见 [`10-终端管控拦截：机制与解决方案.md`](./10-终端管控拦截：机制与解决方案.md) §4）：
> 1. 拦截条件**不是"未签名"** —— 带 Rust 官方数字签名的 `rustup-init.exe` 被同一条规则拦了 8 次；本机大量未签名的编译产物（cargo/rustc/rc.exe 等）却全部正常放行。**最干净的活体反证**：桌面上无签名的 `PdfToImgs v2.0.exe` 至今照跑（详见 10 篇 §4.1）。
> 2. **「以管理员身份运行可绕过」的旧结论已撤回** —— 144 条记录中没有任何一条支持它；同一 MD5 在数小时内被反复拦截，与"提权可绕过"直接矛盾。
> 3. **签名不是"根本解决"** —— 换目录、改文件名同样无效（判定对象是**文件内容哈希**，已有 3 个 MD5 在完全不同的路径下被拦）；唯一有效的路径是"让管控系统认识它"或"不需要创建进程"。

### 4.1 「自己创建一张证书签名」能不能通过验证？—— 本机实测结论

**能通过「链验证」，不能通过「陌生软件策略」。** 这两件事是两码事：前者只取决于「这张证书有没有装进受信任根」，后者取决于管控产品自己的策略。

实测（2026-09-16，本机；只对 exe 的临时副本操作，`Application/` 交付物未改动）：

| 步骤 | 操作 | `Get-AuthenticodeSignature` 结果 |
| --- | --- | --- |
| A | 用 `New-SelfSignedCertificate -Type CodeSigningCert` 造一张自签代码签名证书，对 exe 签名 | `UnknownError` —— 「已处理证书链，但是在不受信任提供程序信任的根证书中终止」 |
| B | 把该证书导入**当前用户**的「受信任的根证书颁发机构」 | `Valid` —— 「签名已通过验证」 |
| C | 撤销（删除证书 + 清理私钥容器） | 回到 `UnknownError` |

结论：

1. **签名机制本身可行** —— 私人创建的证书确实能让本机验证从 `UnknownError` 变成 `Valid`。
2. **但它只在「装了这张证书当受信任根」的那台机器上成立**。换一台没装的机器，立刻回到 `UnknownError`。要全网生效只能让 IT 下发到域/终端 —— 而「把一张私钥在个人手里的自签证书塞进受信任根」本身就是安全团队会拦的高风险动作。
3. **对天擎这类终端管控产品，签名不能解决"被拦"**：其官方加白路径是**文件路径（目录）/ 文件白名单（MD5）/ 扩展名**，判的是文件信誉与策略，不是「你能不能自证」（官方管理员手册 §3.3.1.4）。微软官方文档同样明确：**自签名证书在 SmartScreen 上的行为与「未签名」相同**（OV/EV 有效证书也需积累信誉，且 EV 已不再绕过 SmartScreen）。
4. **但签名仍有一件事值得做**：天擎支持**「文件数字签名设置」——把文件的数字签名名称加白，官方明确"推荐使用该功能加白无安全隐患的自研软件"**（§3.3.1.5）。因为**签名者名称不随版本变化**，IT 加白一次即可覆盖所有未来版本，不必每次发版重新报 MD5。这种场景下**企业内部 CA（AD CS）签发的证书就够用**，不需要买商用 OV/EV —— 天擎比对的是签名者名称字符串，不要求公网信任链。

> ⇒ 一句话：**签名不是为了"通过校验"，而是为了给管控系统一个稳定的加白锚点。** 详见 [`10-终端管控拦截：机制与解决方案.md`](./10-终端管控拦截：机制与解决方案.md) §5-C。

> ⚠️ **必须记住的副作用：签名会改变文件哈希**（实测 `DA140AB54C340A67282634D464D3F993` → `51463444B3FBC5668DE2B964EC349AAC`）。因此：
> · 一旦签名，之前给 IT 的 MD5 白名单**立即失效**，要重新提供；
> · 反之，若已按 MD5 加白，**就不要再动那两个文件**（签名、补字节、重新打包都会让白名单失效）；
> · NSIS 安装包内嵌的 `bcrm-desktop.exe` 是**独立文件**，给安装包签名**不覆盖**它 —— 要签就得两个都签。
> Tauri 侧可用的签名字段：`bundle.windows` 下的 `certificateThumbprint` / `digestAlgorithm` / `timestampUrl` / `signCommand`（需装 Windows SDK 的 `signtool`；本机当前未装，实测可用 PowerShell 的 `Set-AuthenticodeSignature` 替代）。
